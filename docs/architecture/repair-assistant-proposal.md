# DSH Android 独立修复助手（完整方案提案）

**一个独立 APK，复用 DSH，让 AI 根据实际报错动手修。** 用户选好目标、授权本次修复后，AI 自己读日志、追到相关文件、写出改动并验证；不要求用户懂报错，也不要求他逐项批准编辑。原生维护层负责限定访问范围、保留原件、提交和回滚，不负责识别故障或决定怎么修。它不是旧的自动救援：主 App 平时不自动诊断、不因崩溃反复重启；只有用户主动发起修复后，助手才介入。

**当前方向与实现状态：** 用户已纠正为完整复制原版 DSH Android，只增加救援能力，不裁剪原界面、插件、工具、设置或启动流程。当前助手 `0.3.0` 直接编译原 app 源码/资源/主 Manifest，复用全部模块、System WebHost 和正常 EngineManager；仅追加设置中的救援入口、预设/九工具与 native 授权桥。独立 UID 和私有数据仍隔离。`0.2.0` 裁剪版曾有旧门禁通过但实际 Web 因 fileUpload/sessions/uiWorkspace 依赖断裂失败，旧报告不作为新版本证据。本轮中间三 release 构建通过，29 个原 assets/lib 条目相同（排除构建生成的 dexopt/baseline profile），助手比对应 System 约多 60 KB；这不是最新产物最终数字。生产原生授权流在窄 Android stubs 上有局部测试，含首次点击及授权返回先于恢复，准确新计数看最终报告，不是设备证据。完整 Web smoke、最终绑定 L1/L2 和真实 AI/设备修复待本轮报告；L0 既有 mobile 定时器与 npm pack 失败保留。无本轮安装或新上传。

**本文仍含完整目标，不能把下文全部当作现状。** 新增跨包 broker 只开放目标现有 `engine/node_modules/@deepseek-ai/dsh/lib/` 下严格 UTF-8 `.js`，单文件 128 KiB；没有一般 profile/插件/native/lib/二进制修复、多文件事务、完整原始日志或隔离候选执行。每次 broker 激活/回退需原生确认，新 grant 不自动开放旧备份。[repair patch](<../../repair/assistant/src/main/assets/repair-agent/repair.patch.yml>)现在只是追加层，不关闭原服务或限制整个 Agent 工具集合；原模型设置/ConfigEditor 和通用工具保持原样。完整原版的 shell、插件及用户另授 Root/Shizuku/ADB 能力可能绕过 broker，不承诺强制沙箱或所有跨包改动都经过 broker 确认；普通 UID 则不能直接访问另一 App 私有目录。同 UID 通用工具可读取助手信箱并仿造请求，Agent/epoch 绑定只防无意的旧请求跨目标，不是恶意同 UID 代码隔离。准确能力、构建入口和待验项见[实现与验收说明](<../agents/repair-assistant.md>)。

## 1. 一个助手，两个修复目标

| 组件 | 负责 | 不依赖 |
| --- | --- | --- |
| 原版启动与设置中的新增救援入口 | 正常启动直接进入 DSH；设置中选择 System / Gecko 并请求授权，原启动覆盖层保留 native 后备入口；更广回执/导出 UI 仍属目标 | 目标原 App 的主引擎/Web 就绪；普通聊天不等待授权 |
| 助手 APK 内的完整 DSH | 同一 Android 宿主、EngineManager、官方界面、全部原版模块/插件/设置/工具；仅追加救援预设与受控跨包工具 | 被修 App 的引擎、插件、配置、凭据及端口 |
| 原 APK 内的 `:repair` 进程 | 核验助手身份和授权，读取目标私有文件，准备候选，执行事务提交与回滚，提供启动验证证据 | 主 Activity、主进程常驻、Termux、WebView 与特权服务 |

**复用代码，不复用运行状态。** 助手单独安装，使用不同包名、私有目录、`DSH_HOME` 和端口，不使用共享 UID。保留 `com.dsh.android`（System）和 `com.dsh.webview`（Gecko）的现有身份；当前助手 `com.dsh.fixhelp` 同样为 15 字符，接现有 Termux 私有可执行载体并将 targetSdk 设为 28，仍需验证 [Gradle 记录的等长路径约束](<../../app/build.gradle.kts#L48-L59>)及从旧助手同签覆盖安装。完整复用多占一份引擎的安装空间；当前要求不裁剪原版功能与依赖，不以包更小作为成功标准。

助手用自己的模型授权。用户在开启 AI 修复时能看到相关日志和源码可能交由助手配置的模型处理。默认不发送密钥、完整备份、会话内容或无关工作区文件；日志及候选证据同样要按范围筛选并脱敏。没配模型或没有可用网络/本地模型时，AI 修复不可用，不能假装自动修好。原版启动覆盖层的 native 后备入口可请求目标授权；独立导出现场、历史回执和原生回滚 UI 尚未全部实现，不能从入口存在推定这些能力已经可用。

## 2. 主界面打不开时也能授权

1. 主 App 的原生启动层和失败页可以放「打开修复助手」；如果连这两页都进不去，用户直接启动独立的助手。两种主包都安装时，由用户明确选择目标。
2. 助手通过固定 authority 的 `ContentProvider` 握手，Android 在普通进程回收后可按需唤起目标的 `:repair`，不依赖 HTTP、端口或后台常驻。握手只返回协议、版本、目标身份和通道状态，不返回用户数据或日志。
3. 助手从前台打开目标 APK 的原生维护授权页；该页也在 `:repair`，不经过会崩的主 Activity。通道默认关闭。完整目标是明确区分诊断与本次 AI 修复范围；当前源码通过 grant 授权受限证据、读取和候选准备，**每次应用或回退可执行 JS 仍需一次原生确认**，不是模型自动批准。租约为 30 分钟空闲期限；真实用户交互、已绑定 Agent 输出/步骤和工具工作可续期，定时器、空页面或缓存进程不能自行续期。前台通知提供停止操作。停止、到期、设备重启、双方 APK 更新或授权替换后，不允许旧 grant 开始新的操作。未来扩大范围或改变确认策略须另行设计与验收。
4. Provider 和助手可直达的授权页由各 flavor 的 `signature` 权限保护。Provider 在方法和流入口核验真实 Binder 调用 UID 与预期助手包，不信任自报包名；同签名的其他 APK 也不自动放行。两种 release 主包与助手使用同一正式证书，不改已有主包签名。授权和事务状态落盘，普通进程死亡不依赖一条还活着的会话；重连重新校验目标、权限和状态。

现有 [`attachBaseContext`](<../../app/src/main/java/com/dsh/android/core/DshApplication.kt#L62-L72>) 和 [`onCreate`](<../../app/src/main/java/com/dsh/android/core/DshApplication.kt#L100-L136>) 已有非主进程分支，仍需审查更早的类加载、API 26/27 的进程名识别及双 flavor 合并 Manifest。独立进程隔离的是启动故障，不改变同 APK 的文件权限。强制停止、未解锁、包被禁用或安装损坏不保证可唤起，按真机行为提示；旧包未提供通道时，可提示兼容的同签名覆盖升级，不能直接接管。连维护进程都起不来时，只能使用此前保存到 App 外的资料，不建议默认卸载或清数据。

## 3. AI 自己查、自己改，不受固定修复动作限制

| 步骤 | AI 做什么 | 原生通道做什么 |
| --- | --- | --- |
| 读具体现场 | 从这次启动的崩溃栈和日志定位相关配置、插件或已解包的引擎源码；必要时对比同版本官方基线 | 提供带启动标识的证据、授权范围内的目录与文件、当前摘要和只读基线，不向目标执行命令 |
| 编辑候选 | 在助手里的文件副本上直接改配置、修插件代码，或修已解包引擎里的相关源码；可选局部还原，但不强制恢复出厂 | 接收候选的文件变更集，限制目录、类型、大小和数量，校验预期原摘要及文件实际归属；不映射任意路径、不暴露主包实时可写目录 |
| 验证并应用 | 做可用的语法和结构检查，提交改动集；依据本次启动的新证据决定成功、撤回或在预算内继续 | 确认停写、先保留原件再提交，返回回退点；检查整个改动集的状态与实际启动结果，不把单个文件校验通过当作修复成功 |

例如，用户为了开发插件改了引擎的 JS，启动时报 `SyntaxError`。AI 找出栈指向的文件和对应修改，在副本上修那段语法，尽量保留用户添加的功能，再提交并核对新启动。遇到配置字段拼错，也可以直接纠正字段，不必禁用整个插件或让用户清数据。**限制的是可访问范围，不是 AI 能想到哪些修法。**

完整目标拟允许在明确列出的 profile 配置、用户插件文本和已解包引擎文本范围内生成编辑，保留对官方基线的比较能力；**当前源码并未开放这些全部范围**，只允许既有引擎 lib `.js` 的 128 KiB 单文件读写候选，尚无官方基线检索或通用配置/插件修复。禁止写 APK 本身、Termux/Node 二进制、特权 runner、Android 原生组件、凭据、会话和工作区；不提供目标 UID 的任意 Shell、任意文件挂载或递归删除。自动编辑的源码在正常引擎启动时会执行，不能把它当普通文档授权；如果无法将候选试跑与真实凭据、会话、工作区及特权桥有效隔离，生成的可执行候选保持待激活，直到用户看过改动摘要并点一次「应用并试启动」。完整目标可设计按整组可执行改动确认；当前源码按单文件事务确认，尚不支持整组激活。配置、插件源码和日志中的文字只是证据，不能替用户扩大授权或触发上传、提交。

## 4. 应用、验证和失败回退

- 完整协议目标围绕通用文件变更集而非故障菜单：`capabilities` / `status`、受限目录和文件读取、`stageChanges` / `applyChanges`、`jobStatus` / `rollback`、启动验证状态与导出；拟采用元数据和受限流句柄。当前九个工具的精确命名见[现状说明](<../agents/repair-assistant.md#当前源码能力>)，仅传有大小/深度上限的 JSON（Binder 使用 UTF-8 ByteArray，转义后 payload 最多 768 KiB），不提供任意目录流或日志导出；不要将提案中的接口名当作已实现 API。撤销后拒绝新操作，已经交付给助手的数据无法收回。
- **先停写，再留原件，再提交。** 主启动、残留 Node 进程、后台导入和维护操作共用跨进程协调。拿到锁不等于确认 Node 已停；当前正常启动锁覆盖整个 start 至 Node `waitFor`，提交/回退另要求主进程已退出，并扫描同 UID `/proc` 拒绝 Node/engine 命令行和未知状态，防止孤儿进程继续执行。原生一次性确认可请求窄范围 SIGTERM：只关闭复核 UID/PID/启动身份的精确主进程 argv 或精确 Node 可执行文件及目标引擎参数，必须提示请求、终端和未保存操作可能中断；不使用 forceStop/SIGKILL，不碰无关 Node。关闭后仍须通过锁与静止检查，不能确认时只允许读和准备副本，不许覆盖，候选保留。特别要协调 [`applyPendingDataImport`](<../../app/src/main/java/com/dsh/android/core/DshApplication.kt#L183-L215>)。提交前重查目标版本和原摘要；不接受过时计划或路径越界。不能直接套用[普通解包器先删旧目录再重命名的步骤](<../../runtime/engine/src/main/java/com/dsh/android/engine/EngineAssetInstaller.kt#L99-L104>)。
- 当前源码只实现按 grant 分区的单文件 journal 和一次性原生确认，不是下述多文件事务。旧 grant 到期后，新 grant 不能自动列出或回退旧备份，亦无独立原生历史备份恢复入口；不能承诺跨授权随时回退，需后续明确恢复流程。
- 完整目标中候选与回退点留在同一文件系统；持久化请求 ID、旧状态和提交阶段。单文件原子替换不等于多文件事务：在整个改动集发布或回卷之前，阻止正常启动读到混合状态。进程死亡、空间不足、取消或重复提交都不得丢失原件；回滚遇到相同范围的新修改时报告冲突，不覆盖新文件。记录修改摘要、原因和结果，不在审计日志里复制密钥或文件正文。
- 提交完成先显示「已应用，尚未验证」。在本次授权内、且具备合适隔离条件时，助手可自行发起有次数和时间上限的验证；否则用户点一次「打开 DSH 验证」，直接打开所选的**原 App**，不用重装、清数据或导回备份。只把本次启动中引擎与正式 Web 均就绪算作启动修复通过；声称插件功能已修好还需要对应验证，不用历史成功、错误页首帧或解包成功代替。
- 拿到新错误时，AI 可在同一次会话的预算内回退未通过的候选、重做并验证。耗尽预算、证据不足、故障超出授权层或无法确认停写时就停止。能无冲突退回时保留修复前状态；不能安全退回时说明冲突与回退点，不静默丢弃新增数据。会话结束后主 App 不继续监测或触发修复。

## 5. 实现顺序与验收

以下是验收要求，不是本轮通过清单。入口的历史只读验证与新增 runtime/写入源码分别记录；本轮必须重新绑定源码、三 APK、正式签名、模型和设备。当前严格 JS 范围之外的插件/配置用例仍属后续扩展，不能伪装成当前支持或通过。

1. **先证入口。** 双主包加入独立维护页、同签名握手与受限证据读取。模拟主进程初始化、引擎和 Web 各阶段故障，验证主进程未预启动或已崩溃时助手仍能连接。覆盖错签名、同签名错误包、过期授权、旧包及真机强制停止等情况。
2. **再证通用编辑可逆。** 实现候选文件变更集、事务和回滚；先用确定输入测试与真实 Agent 相同的接口。测试运行中写入、并发导入、空间不足、路径超出范围、重复提交和提交边界杀进程。检查会话、凭据、工作区和无关插件状态没有变。
3. **接入 DSH 并验证它真的在修。** 让助手读实际失败证据，分别修一处引擎源码和一处插件或配置错误，不给预先写好的故障映射。验收包括：保留可用的用户自定义改动、从助手启动原 System 和 Gecko、失败后停下或回滚，以及助手自身的 Web/引擎不可用时还能打开原生入口。能编译不等于真机通过。

[事务式启动提案](<transactional-startup-proposal.md>)关注正常升级怎么安全切换；本方案关注已经打不开时，怎样让外部 AI 仍能根据现场修改并验证。两者可共用候选与事务机制，但不要求先重做启动架构。
