# Android 启动与升级：事务式替代方案（提案，未实现）

目标不是在失败后多试几次，而是避免未经验证的升级改写唯一一份可用状态。故障处理入口必须独立于 Node 和 Web GUI。

本文讨论运行资产与数据如何安全发布、切换和回退。主 App 已经打不开时，如何从另一个 APK 诊断、授权和修复，见[独立修复助手提案](<repair-assistant-proposal.md>)；两项设计可以分阶段交付。

## 1. 先保护运行资产，不迁移用户数据

- **只读版本槽**：以内容摘要标识 APK 自带的 Node、引擎、兼容前端和出厂插件组合。保留当前可用槽和上一可用槽。每个槽有清单：资产摘要、Android flavor/ABI、Node ABI、DSH 版本和可读/可写数据格式范围。运行时不在已验证槽内写缓存、安装第三方插件或改配置。版本目录本身不是权限边界；若插件和引擎同 UID，须另行验证隔离能力，不把 `chmod` 当防篡改保证。
- **只在变更时验证**：在同一文件系统的候选目录解包，校验摘要、空间、文件权限和兼容性；用独立端口和隔离的临时状态做启动与桥契约验证。校验失败只保留报告，活动槽不动；不在日常冷启动额外跑一次引擎。
- **一次提交**：候选验证成功后才原子发布活动版本指针；在实现中明确文件与父目录持久化、并发锁和中断重入。验证前后任意位置被杀或磁盘写满，重开只能看到完整的旧槽或完整的新槽，不猜测半写目录是否可用。

## 2. 把运行资产回退与数据回退分开

- 会话、凭据、工作区和用户插件开关继续独立保存。只有确实改变数据格式的升级才触发显式、版本化迁移；在一致性快照或受控写入窗口内迁移到新世代，预验后同时激活匹配的运行槽和数据世代。不得用真实凭据或可写工作区做候选试跑。
- 旧引擎能读当前数据时，只回退运行资产；不能读时原生界面明确列出兼容性、数据世代和影响。用户在保留并可导出新数据后才可以选择旧快照；不能用自动回退吞掉升级后的新会话。
- 插件先固定解析版本和依赖，验证新增/变更插件的候选版本；单插件故障只报告该版本，不偷偷改 registry、用户禁用项或其他插件。真正做到「单插件崩溃不拖垮主进程」需要上游支持故障边界或独立进程；同进程内的 `try/catch` 不能处理 OOM 或 native 崩溃。没有隔离能力时明确报告，不能承诺继续运行。

## 3. 独立原生故障页与验收

原生页显示失败阶段、版本及证据，提供查看日志、诊断和数据导出、手动重试与可用的回退选项。超时只说明「尚未就绪」；不以 DOM 探针、日志措辞或失败次数作为改写状态的授权。

优先交付运行资产事务；确认占用预算和进程写入边界后，再设计数据迁移及插件隔离。验收至少覆盖解包/提交中强杀、空间不足、资产摘要错误、损坏的候选插件、不可逆数据迁移、升级后新增会话再回退、双内核渲染进程退出。每一项同时检查运行结果和原用户状态是否不变，不能只看「界面打开了」。
