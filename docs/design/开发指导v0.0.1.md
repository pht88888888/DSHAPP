# DSH 安卓化开发指导 v0.0.1

- 日期：2026-10-22。
- 状态：已确认需求的工程实施指导，尚未开始项目构建或 Android 验证；任务表不是完成记录。
- 设计依据：[设计说明 v0.0.2](设计说明v0.0.2.md)；历史材料：[设计说明 v0.0.1](设计说明v0.0.1.md)。发生冲突时先修订文件并记录决定，不让实现自行选择更宽松的一份。
- 适用开发方式：用户配合 AI；电脑当前未安装 Android 开发工具，先用 MuMu，辅以用户手机；没有工期承诺，完整实现并验证稳定后侧载发行。
- 本文不授权安装工具、Root 手机、修改官方运行中实例、提交代码、推送或发布；实际执行各步时再确认目标路径、设备和必要权限。

## 1. 本项目的完成定义

做的是“本地完整 DSH 运行平台”，不是只加载聊天页面的 APK。保留真实命令、PTY、锁、插件、子代理、后台作业、持久化会话及审批；实现双 DSH 内核、A/R/E、确定性恢复、事务更新、加密备份、布局、系统悬浮窗、设备自动化和已确认的相机/音频/视频/位置/蓝牙/传感器/Shizuku/Root 能力。

阶段成果只用于开发与验证，不等于发布版。不得把“接口存在”“返回 NOT_SUPPORTED”“模拟器可启动”“APK 打出来”“配置能转储”单独当作完整首发通过。支持硬件缺失时允许准确拒绝，但该能力仍须有支持设备上的正向证据。

### 1.1 已定约束

| 约束 | 工程执行规则 |
| --- | --- |
| ARM64 侧载优先 | 首发正式运行载荷为 ARM64；targetSdk 28 先做原型验证，安装/执行限制据实记录。不要默认商店发行或支持所有 Android。 |
| 保持官方语义 | 允许最小 Android 平台兼容补丁，但不另写 Agent、会话或认证协议，不发明新插件标准。 |
| 可信插件 | 诚实表达合作式限制；用户态拦截不是强沙箱；不能通过默认全权或禁用锁伪造兼容。 |
| 高效精简 | 整机基准 4GB/64GB；正常只运行 A，R/E 按需，系统 WebView 优先，媒体与设备模块懒加载。 |
| 完整首发 | 本文件阶段 G0–G9 全部完成，设计说明第 11 节 1–40 有可追溯证据，才进入发行。 |
| 可停机维护 | 管理操作可等待或提示停止任务，不能确认停写就拒绝；一致性高于无感更新。 |
| 整目录加密备份 | A profile、插件目录及声明关联内容原样合包，用户设置密码；不退回只备安装清单或脱敏插件文件。 |
| 备份触发 | 每次正常成功进入 A 后自动安排一版，另有手动备份；不依赖退出/强杀回调；维护续启不得循环触发。 |
| 不丢数据 | 新版已有真实写入后不得自动覆盖旧快照；K2/E 是修复工具，不直接接管不兼容新版数据库。 |

### 1.2 尚需采集但不应继续扩展的产品信息

第一次实际开发时登记 MuMu 的确切版本、镜像 Android/API、ABI 与 ARM64 转译方式；手机型号、Android/API、ABI、WebView、可用存储及厂商后台策略；电脑 CPU/内存/空闲磁盘/虚拟化。用户尚未提供这些数据，文档不填猜测值。

相机、位置、BLE 等按设计说明 4.14.1a 的已确认用途实现，不另开一轮无限需求征集。新增云通话服务、所有蓝牙厂商协议、所有 Android API 不在“全部实现”承诺内。

## 2. 先建立工程与证据，而非直接开写 APK

### 2.1 建议仓库组织

以下为待建立的逻辑目录，不是现有仓库事实；能用一个 Gradle app 模块先实现就不急着拆成大量构建模块。

```text
android-app/                 APK 外壳与 Kotlin/必要 native 实现
  supervisor/                实例、作业、事务、恢复调度
  runtime/                   运行资产部署、启动、PTY 与前缀处理
  gateway/                   协议、授权、能力路由
  backup/                    快照、加密、SAF 发布与导入
  platform/                  设备、媒体、悬浮和增强权限实现
  web/                       WebView 生命周期与受限原生桥
bridge-sdk/                  DSH 标准插件可用的版本化桥 SDK
plugins/android-base/        “安卓基座”设置、诊断和状态交互
adapters/official-dsh/        锁定官方版本的事件/管理/认证适配
adapters/layout/              唯一布局执行者
patches/                     Android 最小兼容补丁与审计说明
assets-manifests/            运行时、K1/K2、救援与发行清单
scripts/                     可复现构建、打包与校验入口
tests/                       契约、集成、故障与设备测试
docs/decisions/              ADR 与已验证/失败路线记录
docs/evidence/               脱敏证据索引，不存秘密或大二进制
```

依赖方向：业务插件 → SDK → 原生网关 → 系统适配器；监督器独立于插件和模型，原生恢复独立于 Node 与可选媒体。加密/归档、事务存储等低层模块不反向依赖 DSH 设置页面。不要把 Kotlin 内部类型暴露为社区插件 ABI。

### 2.2 首批工程文件

- 构建环境说明：实际 JDK、Gradle Wrapper、AGP、SDK/Build Tools、NDK（确有 native 构建才安装）、Node、包管理器及 Windows 构建命令。
- 上游锁定清单：官方 DSH、DSHAPP、AndriodTablet 参考分支的提交，全部资产来源、哈希与许可证。前轮审查的官方提交是 `687f282e8625c6b8d11ff58211a90524be2e4317`，不是已经选择好的首发版本。
- 补丁清单：preimage → patch → postimage 哈希，修改原因、回归测试与撤销条件。
- 能力矩阵：Android/API、ABI、target、WebView、K1/K2/Node/桥版本、插件测试集。
- 证据格式：测试 ID、时间、源码/构建哈希、设备/镜像、步骤、期望、实际、通过/失败/不适用、脱敏附件与缺陷链接。没有执行的写“未执行”，不能从参考项目测试文件复制“通过”。

### 2.3 Windows 初始准备顺序

1. 用户确认开发机与设备信息，确定新的实现源码目录，不把本设计资料目录误当已有 Android 工程。
2. 审查参考项目的许可证、构建说明、包名/ELF 前缀约束；在确定 applicationId 之前完成核对。
3. 经用户许可安装 Android Studio 或必要命令行组件，优先使用项目 Gradle Wrapper；JDK/AGP/NDK 选兼容的一组并锁定，不盲目安装“全部最新”。
4. 配置开发专用签名与本地签名变量；正式签名私钥离线备份，不写入源码或 AI 对话。
5. 通过 adb 列举 MuMu/手机，后续命令显式指定设备序列号，避免误装到其他设备；手机 USB 调试与敏感测试由用户确认。
6. 构建最薄 APK，安装、启动、卸载测试仅使用可丢弃测试数据；保存可重复构建命令及结果。

MuMu 不等于标准 AVD，不能承诺任意 API 镜像可调。版本覆盖应按实际可获得镜像、手机及必要额外测试设备安排；x86_64 或 ARM 转译通过仅是辅助证据。

## 3. 工程闸门与依赖顺序

```text
G0 环境/来源锁定
 ↓
G1 单 A 可行性 + 四个路线闸门 + 账号登录
 ↓
G2 监督器、A/R/E、完整救援闭包
 ↓
G3 管理协调、快照、事务更新与原生恢复
 ↓
G4 用户密码加密备份、启动事件调度及恢复
 ↓
G5 官方 GUI 布局/设置/插件兼容
 ↓
G6 系统悬浮、声明式行为及多通道流基础
 ↓
G7 设备采集、自动化与增强权限完整实现
 ↓
G8 模型诊断修复、资源/故障压力闭环
 ↓
G9 三类产物、迁移回归、完整验收后发行
```

这是集成顺序，不禁止已稳定接口后的有限并行。相机/蓝牙等在 G3/G4 期间可做独立可抛弃实验，但不得抢占 G1 的路线结论或把实验直接当成集成完成。用户一人配合 AI 时默认逐步集成，避免同时开启多个互相改协议的代理。

### G0：开发底座与合法可复用来源

**目标：** 从未配置开发工具的电脑，获得最小可复现构建与明确的上游资产清单。

**任务：** 完成 2.2/2.3；审计 DSHAPP 的安装前缀、Termux 资产、Node native 绑定、锁/PTY/runner 补丁与单实例假设；检查开源代码和二进制的分发义务。不要先复制整个项目再不知道改了什么。

**验收：** 干净环境可按锁定步骤构建/安装薄 APK；所有输入有可取得来源及哈希；包名满足已选部署路线；实现仓库与运行中 DSH profile 分离。

**不通过：** 缺少来源、许可证义务不清或不可复现资产先作为阻塞项处理，不用已编译 APK 冒充源码可维护。

### G1：单 A 跑通，并裁决四个路线闸门

**目标：** 证明这条 Android 路线能提供真正的 DSH，而不是先做一堆 UI。

**实施顺序：**

1. 部署封存的 Node/必要工具和官方 DSH 基线，建立独立 A HOME，启动官方 Web GUI，认证本地连接。
2. 测真实命令 stdin/stdout/stderr/退出码、管道、信号、取消、PTY 输入/resize/断线重连、文件搜索读写/链接/原子替换。
3. 用并发写者验证文件锁真实互斥；验证子代理、后台任务及遗留后代，不能通过跳过 Android 平台锁检查完成。
4. 核对 runner/sandbox 的状态报告，对“允许路径、禁止路径、拒绝反馈、审批模式”做成套实验；LD_PRELOAD 只能如实声明合作式约束。
5. 核对 targetSdk 28、正式 ARM64 载荷与私有目录执行在手机上的安装/执行限制；必要补丁逐个登记并保持官方业务语义。
6. 一个 Host 工具插件与一个 Client 页面/Slot 插件按官方机制安装、激活、调用和卸载。
7. 官方账号 Web 发起 → 系统浏览器/Custom Tabs → 官方 Host 回调/确认 → 实际受认证操作；测取消/超时/重启和环境归属。复核锁定源码的 state/PKCE/localhost 流程，不假定移动浏览器的 localhost 一定回到正确服务。无主动刷新能力时按官方规则重新认证。
8. 做一次官方安装/HMR 与快照竞争实验，选择可行的管理协调接缝；不能在线统管则明确采用维护窗口。

**四个闸门：** 平台兼容、安全表达、发行执行、管理协调。每项分别提交通过证据或失败与下一决策，不合并成“基本可用”。官方登录是额外硬阻断项，也必须在本阶段验证。

**失败处理：** 先尝试允许范围内的最小平台补丁；需要禁用锁、假报 full enforcement、改变认证、后台无限重试或无法停止写者时不进入下一阶段。调高 target/改 ABI/换整套执行方式属于路线变化，需重新验证而非修改文档宣称通过。

### G2：监督器与完整救援闭包

**目标：** K1/A、K1/R、K2/E 可控，插件/Node 坏了仍有原生恢复入口。

**任务：**

- 先初始化监督锁、事务对账与无扩展恢复入口，再准备 Node/Web/悬浮媒体。
- 建立实例描述与受管作业账本：环境、epoch、内核/运行时、HOME/profile、工作区、地址、PID 与可用出生标识、任务/PTY/代理作业、desired/observed 状态。
- 实现有界启动/停止与 A→R→E；页面、服务、进程和桥健康分别判断，白屏先修页面，模型网络错误不切内核。
- R 不读取 A 用户工具链启动脚本；E 固定 K2/profile/Node/原生库/桥适配/最小工具的完整依赖闭包，版本引用不能被普通包管理覆盖。
- 对 Termux 固定前缀、加载器、动态库、pnpm 外部链接生成真实解析清单。目录分开并不代表实际加载分开。
- 不能确认写者退出时只读，不按进程名乱杀；提供用户强制停止应用/重启设备后的重新核验流程，外部高权限作业另行确认。

**验收：** 断网，移走或损坏 K1/A 可变来源并检查哈希，E 仍启动；同时损坏两套 Node，原生入口仍可导出最小脱敏诊断、停用扩展和导入可信恢复包。模拟宿主死亡、setsid、双重 fork、PID 复用、旧 epoch 请求，不能双写或误杀。

**说明：** K2/E 不随 A 常驻；初次发行可以使用同一个已验证官方版本分别部署两套独立依赖树，只要救援组合独立且完整，不能为了“版本不同”选择未经验证的旧版。

### G3：单写者、诊断副本与事务更新

**目标：** 代码、profile 图、配置和数据迁移一起提交，并能解释任意中断点。

**任务：**

1. 定义监督锁 → 环境管理锁 → 资源/备份发布锁的固定顺序，禁止边持锁等待用户无限输入；批准后再取锁并复核条件。
2. 官方管理入口按已验证接缝协调；无法捕获直接命令/HMR 时，维护窗口阻止新入口并停全部已知写者，再检验源 revision/哈希，不声称目录锁可阻止任意同 UID 写入。
3. 停写后复制 profile 及必要安装布局；`--dump-config` 只在诊断副本执行。比较原 A 的文件树/必要元数据不变，副本规范化不回写；不能在 Kotlin 重写一套不兼容 Loader。
4. 实现阶段持久日志、恢复引用与激活组合：PREPARED → DATA_READY → TRIAL → COMMITTING → COMMITTED；单一可判定提交点，不各写一个互不相关的“当前版本”。
5. 更新包签名/哈希/尺寸验证，安全解包，最终树封存。运行时、K1/K2、桥、profile revision、schema/迁移一并绑定。
6. 候选在独立 HOME 验证且不接真实任务。可信插件仍可能在加载时联网或执行代码；无法限制副作用的检查改成经授权维护实验，不能宣传成强隔离。
7. 新版真实写入前失败可撤候选；写入后按兼容降级或授权的数据处理恢复，禁止自动拿旧快照覆盖新会话。

**验收：** 对每个阶段“记录前/记录后、关键文件操作前/后、提交点前/后”注入进程死亡并重启；最终是完整旧组合、完整新组合或清楚的只读恢复，不出现混搭。不删唯一救援引用，不用“JSON 已写”代替断电一致性测试。

### G4：完整目录加密备份与启动调度

**目标：** 用户设置密码，首次配置后每次成功进入自动生成一版；卸载/重装输入密码可恢复文件组合。

**先做独立实验，后做 UI：**

- 从真实 profile/插件安装树构造测试样本：点文件、二进制、空目录、权限、内部链接、pnpm 外链、目录内假 token、范围外秘密与特殊文件。
- 定义完整备份清单与实际依赖映射；目录内内容原样保存。对范围外闭包必须明确收集或列缺项，不能随意裁剪或追随任意路径。
- 选一个维护中的密码 KDF + 认证式流加密库/容器并锁定，优先复用标准实现，拒绝自创加密算法。必须支持内容/清单保密、分段/整包完整性、截断/重排检测及跨设备密码解锁。先比较成熟完整容器与成熟流加密库封装两条路线，再用往返/篡改和资源实验裁决，不在本文假称某库已经可用。
- 冻结格式版本、库/算法 ID、KDF 允许上下限、盐和 nonce 规则、认证头、终结语义、元数据泄露范围、密码编码/长度、密码世代与导入配额。小数据及大目录往返均校验逐文件哈希和元数据。
- 用户输入密码与确认；本机为自动备份只存 Keystore 包裹密钥材料，不写明文密码。不依赖原 Keystore 的独立解密测试必须通过。改密码只影响新包，旧包仍需旧密码，界面告知。

**自动触发状态机：**

```text
正常 A 激活(eventId, origin=user-entry)
  → 服务 + 必需桥就绪、页面归属已确认
  → 未配置：待设密/目录，提示而非成功
  → 已配置：PENDING → WAITING_FOR_QUIESCE
  → 用户确认/无写者后：SNAPSHOT → RESUME_A
  → ENCRYPT → VERIFY → PUBLISH → ROTATE → SUCCEEDED
任一安全条件不满足：FAILED/BLOCKED，保留旧包并显示原因
```

- eventId 是用户进入事件，不是 Node 每次重启的 epoch；用于备份的维护续启标为 origin=maintenance-resume，继承原 eventId，不新建备份请求。
- 一个 eventId 最多发布一个完整成功包。进程重启先对账请求/备份 ID；发布成功但尚未记成功时不能再次生成一版挤掉旧包。
- 旋转、网页刷新、短断线、普通回前台不触发；新正常 A 激活触发，R/E 不入用户包。账号离线/过期不阻止文件备份。
- 首次未设置密码/目录时在设置页引导并保留待办；用户未配置不阻止 Agent 基础使用，但不得标成功。
- 不静默停止用户任务；忙时等待或请求维护确认，不能确认停写就失败。先快照，再续启 A，压缩加密从快照执行；续启失败与快照/备份结果分开显示。
- 无退出备份要求；强杀不承诺回调或最后一刻备份；上次备份是进入时状态而非后来所有更改，界面提示重要变更后可手动备份。

**SAF 与保留：** 私有一致快照 → 流式压缩/加密 → 用户 backup 临时对象 → 读回校验/完成提交 → 更新账本 → 删除最旧所属完整包。默认三份完整成功包，部分/失败不挤占；开始前为快照、第四份与应急恢复预算预留空间。无需假定 SAF rename 原子，按所选提供方实际语义实现并对账。

**导入：** 用户选包/输密码 → 限制未认证 KDF 及资源参数 → 私有暂存解密认证 → 安全展开 → 展示范围/兼容/缺项 → 用户批准 → 当前 A 恢复点 → 候选验证 → 事务提交。全包认证与安全检查完成前不执行插件或写回 A；不自动批准构建脚本、设备权限或账号授权。

**硬验收：**

- A 原目录与解密后目录内容/依赖图符合 manifest，不只比较包能否打开；范围内假 token 应原样在解密私有结果中，绝不能出现在 SAF 明文或诊断。
- 错密码、篡改头/块/结尾、截断、超大 KDF、路径穿越、解压炸弹均拒绝，无未认证内容执行。
- 重装并重新授权目录、不使用旧 Keystore，输入密码可读旧包；忘记密码不提供假恢复。
- 自动/手动连续四次后只有三份受管完整包；模拟断网提供方、断权、写满盘、取消、清理失败、部分闭包和同一 eventId 宿主崩溃，不提前删旧包或重复轮换。
- 手动备份、首次待办、自动触发、维护暂停恢复及失败重试均可观测；不会备份→重启→再备份死循环。

### G5：官方 GUI、唯一布局适配与社区插件

**任务：**

- 基座只做容器和受限系统桥；日常设置统一在官方“安卓基座”插件设置。需要停止后端的维护进度走已加载 Client → 原生桥，不能请求已经停止的后端。
- 原生窗口提供稳定的实际应用尺寸与 IME 信息；LayoutAdapter 是唯一布局执行者，auto/mobile/official 及滞回阈值保持设计说明，不用键盘缩小后的 visualViewport 误判方向。
- 不兼容 DOM 的局部输入区/顶栏增强关闭并回官方界面；清理样式、监听、观察器与借用控件。适配资源与 APK 版本戳匹配，禁止重复安装两个布局执行者。
- SDK/插件遵循目标官方 Loader、Host/Client、Config、Tool/Event/Service/Slot 契约。正式写插件前加载相应 Cordis 技能，用 Inspect 或锁定版本源码查真实接口；Inspect 不是可在业务代码中直接调用的 Service，不猜 API 名。
- 代表集：Host 工具、Client 页面/Slot、配置事件、stdio MCP、原生依赖、Android 能力。沿官方流程完成首次安装、升级、重启、禁用、卸载及清理；未知兼容仅提示，不自动禁止官方安装，也不默认批准脚本/权限。

**验收：** 横竖屏、分屏、键盘、页面重载不丢草稿/任务/会话；GUI 与内核健康分离；设置写回无历史覆盖；六类插件分别有安装/Host/Client/权限/功能结果。

### G6：悬浮系统、声明式行为及流基础

### G8：模型诊断、压力与故障恢复闭环

**任务：** 在确定性恢复已通过后实现 R/E 的模型诊断、修改建议、受控修复和结果核验；独立配置模型，模型离线仍能日志/备份/导入/还原。修复计划声明范围与不可逆副作用，批准绑定目标/参数/环境/epoch/通道/有效期，执行前再核验。

按设计 6.5.5 的故障表与第 8 节预算跑压力：磁盘写满、日志洪泛、任务扇出、低内存、播放器崩溃、共享运行时损坏、进程遗留、授权撤销、审批后目标替换、网络中断。基础自动化不能操作自己的可信审批，不以插件自报 approved 通过。

**验收：** 控制面可重入、故障有界、损坏资源能停用、无模型不失去确定性恢复；只读状态存在人工解困路径；已执行/不确定副作用不假报已撤销。修复模型不能替代监督器决定是否允许写 A。

### G9：三类同源产物与完整首发验收

**任务：** 由同一已校验核心资产构建全量 APK、基座升级 APK、内核升级包；APK 同包名/签名体系与 versionCode 规划，构建清单可追溯。升级 APK 自身完整可运行，不以旧 APK 内残留文件为前提。

- 干净安装 V 与从旧版升级至 V 的程序资产/默认能力一致，用户数据只做声明迁移。
- 基座 APK 误用于首次安装不白屏，给可信内核导入/部署入口；断网升级后仍有至少一个完整救援组合。
- APK 覆盖不覆盖 profile/插件/模型/会话/工作区，不能承诺普通应用随意降级 APK。
- 更新信任根、包签名、密钥轮换、来源、历史可信回滚授权分别说明；备份密码不是软件发布签名密钥。
- 发布支持矩阵、已测插件、资源目标及已知限制；明确“官方基线 + Android 最小兼容补丁”“可信插件，非强隔离”。附许可证/来源与补丁说明。

**发行门：** 设计第 11 节 1–40 均有测试记录与结论；不适用必须由硬件/API/授权条件证明且不掩盖未实现。无未解决的数据丢失、秘密泄露、虚报隔离、双写或救援闭包缺陷；用户完成手机验收与稳定使用后人工决定发布。不自动提交、签名发布或上传。

## 4. 关键接口：先冻结语义，再选传输

以下是本项目待实现接口草案，不是官方已存在的 Service/Tool，也不是允许任意程序调用的现成授权口。具体命名/schema 在实现时对照官方检查结果确定。

### 4.1 两种有效组织方式

共同场景：设置页请求手动备份，允许等待维护，随后查询结果；任一方案都要求同一个事务 ID、去重、权限与取消语义。

| 方案 | 相同场景调用示意 | 取舍 |
| --- | --- | --- |
| 按领域的类型化门面 | backup.create(request) → operationId；operations.get(operationId) | 调用可发现、参数易验证，领域方法增多需维护 SDK；推荐对插件暴露 |
| 统一命令总线 | dispatch({method:'backup.create', payload:request}) → operationId；dispatch({method:'operations.get', payload:{operationId}}) | 传输/版本路由统一但方法名与 payload 易错；推荐仅作网关内部协议 |

组合建议：SDK 类型化领域方法，内部走统一受认证命令包；同一个 schema 生成/校验两侧绑定，避免同时手写两套规则。传输在低频文件队列、受认证本地 HTTP/WS 等中实验选择，原生 API 不与某种信箱文件名绑定。该建议不授权新增任意公共 API，重大契约变化先确认。

### 4.2 最小契约示例

```ts
// 仅作项目契约草案；输入的用户身份/批准不能由插件自行伪造。
type BackupRequest = {
  environment: 'A';
  idempotencyKey: string;
  sourceEventId?: string;
  reason: 'manual' | 'entry';
  expectedProfileRevision?: string;
};
type OperationRef = { operationId: string };
// create(): 接受请求，不等于已完成备份。
// get(): 返回 pending/waiting/running/succeeded/failed/cancelled、阶段与结果。
// cancel(): 请求停止尚可阻止的步骤；不能抹掉已提交包或已执行副作用。
```

常规用例：create → 查询/订阅 → 用户确认维护 → 成功返回 backupId/complete/verified/published。失败用例：源 revision 变更、未知写者、密码未配置、Keystore 锁定、SAF 断权、空间不足、校验失败。超时后按 operationId 查询，不能换 key 盲目重试。备份目标 URI/密码材料由受信设置流程登记，普通插件请求不提交明文密码。

统一请求包至少含 protocolVersion、environmentId、epoch、requestId、method、deadline、payload；授权上下文由网关确定，不能信任 pluginName/approved 字段。结果区分“收到”“已提交配置”“资源就绪”“实际生效”。

### 4.3 错误、资源与版本规则

- 草案错误类别：NOT_SUPPORTED、PERMISSION_DENIED、APPROVAL_REQUIRED、STALE_CONTEXT、BUSY、TIMEOUT、CANCELLED、INTEGRITY_FAILED、INCOMPATIBLE、INSUFFICIENT_SPACE、AUTH_REQUIRED、INTERNAL。备份密码错误应与官方账号认证错误分开映射，不原样向用户抛秘密堆栈。
- 流句柄绑定所有者/epoch/期限，订阅可撤销，队列有界；环境切换、卸载或撤权后按类别清理。
- GUI 断连不自动取消 Agent/PTY；观察事件有界重连；采集撤权即停止。不能用统一 dispose 误杀全部任务。
- 主版本不兼容拒绝；可选能力缺失局部降级，首发必需实现不能以可选开关永久隐藏。桥、SDK、官方适配器、运行时分别记录版本。

## 5. 更新、备份和修复共用的事务规则

| 操作阶段 | 可以取消什么 | 不能声称什么 |
| --- | --- | --- |
| 等待授权/等待任务/下载/校验 | 未执行步骤、可丢弃临时输入 | 超时就是没执行 |
| 停写/建立快照 | 依安全点恢复原实例并保留必要对账 | 已请求 stop 就等于已停 |
| 压缩加密/候选准备 | 停止任务、标记并清理未完成产物 | 半包可恢复、原 A 已更新 |
| 提交关键区 | 先完成可判定提交/恢复，再响应取消 | 任意时刻都能瞬间撤销 |
| 已提交/已发布 | 后续另发受控恢复/删除任务 | 取消自动抹掉新数据/旧副作用 |

原生持久存储方案可选受验证 SQLite 或原子文件日志，但选择前必须通过系统回收/断电模型实验。不要同时维护两个未经事务关联的激活真相来源。SAF 发布与私有事务不是一个原子文件系统事务，必须定义可重启对账和幂等发布。

诊断副本、管理恢复点和用户加密包是三个对象：前者不回写 A，中者按声明范围恢复一致组合，后者用于插件/配置迁移且可能有时间滞后。不能拿启动时的三份用户配置包代替升级前数据快照。

## 7. 补丁与供应链纪律

- 上游版本锁定；补丁越少越好但不为了数量隐藏二进制替换。原始发行物与打补丁结果各有校验。
- 每个补丁一个原因和一个回归，升级时 clean apply + pre/postimage + 功能测试；上游已支持就优先去补丁。
- 原生绑定按 ABI/Node ABI 编译验证；不要把 Windows/Linux glibc 二进制当 Android Bionic 载荷。
- 包构建脚本按风险审批；可信插件也不等于永久批准所有安装脚本和设备权限。
- 签名私钥、账号秘密、备份密码分别管理；公开证据只用测试秘密/脱敏结果，原始 stderr 不无限落盘。
- 参考仓库 main/分支链接会变，锁定提交后再写“与本版本匹配”；本轮仅修订文档，没有重新全量审计参考代码。

## 8. 4GB／64GB 下的资源与性能计划

### 8.1 首轮目标，不是已测结论

以下为待 G1 基准校准、G8 冻结的工程目标；若实验表明不现实，记录瓶颈与调整理由，而不是伪造通过或删除功能。新增明确产品性能承诺须用户确认。

| 项目 | 首轮建议目标/方法 |
| --- | --- |
| 日常空闲 | 测 APK/服务/WebView/Node 等受管进程总 PSS，先以不超过 1GiB 为优化目标；R/E 不同时常驻 |
| 典型任务 | 以总 PSS 不超过 2GiB 为压力观察目标，记录系统可用内存、峰值与 LMK；Android 自身内存不计为应用预算 |
| 子代理/任务 | 默认保守调度（如主作业加一个子作业），允许排队/取消；不能靠完全禁用子代理过关；编译器子进程另行统计 |
| 冷启动 | 已部署、无联网依赖时，手机上以 30 秒内 GUI 可交互为首轮目标；首次解包另测，不混用 |
| 快照停写 | 用固定 100MiB 配置/插件样本先以 5 秒内为优化目标，记录文件数与实际结果；大包超限应明确进度，不假保证任意目录都很快 |
| 大目录备份 | 1GiB 样本验证流式处理，无与包大小等比的 RAM 占用；速度、额外 PSS、磁盘高峰和耗电均实测 |
| 应急可写空间 | 初始按 256MiB 观察预算加实际事务/诊断需求评估保留方案；不是报表上减一个数就可称为已预留 |
| 存储准入 | 可用空间必须覆盖快照、候选、第四份密文、SAF/私有暂存与应急余量；根据实际清单计算，不拿“64GB”作可用量 |

只在同设备、同镜像/系统、同测试数据、同 WebView 和版本下比较；先做一次预热，再至少 10 次冷/热样本，报告中位数、P95、最大值与失败数。少量样本的 P95 仅作工程观察，不能当稳定统计承诺。

### 8.2 优化顺序

不同时运行 A/R/E → 移除默认双 Web 内核和无用大依赖 → 按需工具链与模块 → 媒体可见性/帧率控制 → 有界日志/流缓存 → 优化快照/归档 I/O → 最后考虑复杂共享/去重。

初期用独立完整树换取救援正确性，可对已封存且不可变、生命周期清楚的内容做验证后的去重；不得共享可变 node_modules 或让日常安装破坏 E 来省空间。系统回收仍可能发生，重启对账比“保证永不被杀”更重要。

## 9. 用户配合 AI 的单任务执行模板

每轮只给一项可验收任务；先读仓库指令与当前改动，不凭设计草案编造现有 API。不默认多代理、全局升级依赖或修复运行中 profile。

```text
任务：对应阶段 + 一个具体行为
依据：设计条款 / 验收编号
环境：源码版本、设备序列号、ABI/API、实际运行地址（如适用）
前置：已通过的闸门与证据
允许改动：明确目录/文件；保持已有用户改动
禁止改动：Agent/会话/认证语义、无关插件、秘密、发布与全局环境
实现：先调查真实接口，再做最小改动
测试：明确自动测试命令、设备步骤、失败注入与通过条件
交付：修改摘要、已跑/未跑测试、脱敏证据、风险及回退方式
停止：缺权限、无法验证或触及禁改边界时说明，不假装完成
```

需要并行时只拆不重叠范围，例如固定协议后的相机与 BLE 实现；协议、监督器事务和发布入口由一个负责人集成，所有并行改动最后统一审 diff 和回归。没有必要不引入额外协调系统。

每个小步先保留可运行基线，再测试、再人工确认是否提交。若用户没有要求提交，保持工作区改动不自动 commit/push。失败报告保留字面错误、环境、最小复现和实际副作用，避免“差不多成功”。
