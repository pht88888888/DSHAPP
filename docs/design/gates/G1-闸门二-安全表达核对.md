## 2. 核对结果

### 2.1 用户可见文案：无夸大

| 检查项 | 结果 |
|---|---|
| 是否出现「完全隔离」「安全隔离」「强隔离」「内核级隔离」 | ✅ **零命中** |
| 「特权权限」页的表述 | ✅ 准确（见 2.2） |
| 「root 权限」页的表述 | ✅ 准确且主动说明误判情形（见 2.3） |

### 2.2 特权权限（uid 2000）

原文：

> 开启后，AI 可以在需要时以更高身份执行命令 —— 截图、模拟点击、卸载应用、
> 改系统设置这些原本做不到的事。**默认仍走 App 身份**，要不要提权由 AI 自己判断。

**评价**：如实。说明了「默认不提权」「由 AI 判断」，没有暗示这是安全边界。

状态三态也分得清：`已开启` / `未开启` / `检测中` / `检测失败` ——
没有把「检测失败」含糊成「未开启」。

### 2.3 root 权限（uid 0）

原文（节选）：

> root 工具只在检测到 uid 0 时才注册。检测方式是真的跑一次 `su -c id -u`、
> 看输出是不是 0，而**不是查 su 文件在不在** —— **占位 su、装了 Magisk 但没授权、
> root 升级后失效**这三种情况文件都在却提不了权。

**评价**：这是本次核对里**最诚实的一段**。它主动列出了三种「文件在但提不了权」
的误判情形，正是设计说明要求的「如实报告合作式限制」。

`rootNextAbsent` 还明确说了：

> 本机没有 root（也没找到 su）。需要 root 的功能用不了，**其余功能不受影响** ——
> 上方的 uid 2000 通道与之无关，照常可用。

**评价**：没有把「没有 root」表述成「功能残缺」。

### 2.4 sandbox 的真实定位

`docs/agents/sandbox.md` 的标题就是：

> **④ Android 没有内核级沙箱后端**

正文明确：

> ⚠️ **与真 bwrap 的差异**：`--unshare-pid` 无法实现（同样缺 CAP_SYS_ADMIN），
> **PID 命名空间没有隔离**。**文件写边界是完整的，那是本方案承诺的部分。**
> `--ro-bind / /` 也不做只读挂载，靠拦截器拦写。

**评价**：这是准确的能力声明 —— 承诺「文件写边界」，明确否认「PID 隔离」。

### 2.5 关于 `enforcement: "full"`

`writeSandboxPatch()` 生成的 overlay 没有显式设 `enforcement`，走引擎默认。
初看像「假报 full」，核实后**不是**：

引擎里 `STATIC_ENFORCEMENT` 的语义是「**承诺的文件效果被完整治理**」，
不是「完整的内核级隔离」。原文注释：

> `bwrap` and Seatbelt govern every promised file effect by construction,
> so **the claim is a profile fact**

即：`full` 描述的是「这个后端能治理它承诺的那些效果」，而 Android 方案承诺的
就是「文件写边界」—— 这一条确实被 `boosandbox.c` 的拦截器完整覆盖。
PID 隔离不在承诺范围内，也从未声称有。

**结论**：不构成虚报。
