## 3. 包名与前缀路线（锁定）

### 3.1 已锁定

| 项 | 值 | 依据 |
|---|---|---|
| `applicationId` | `com.dsh.android` | 15 字符，硬约束 |
| `namespace` | `com.dsh.android` | 同上 |
| 变体 | `system`（系统 WebView）+ `gecko`（GeckoView） | 两个 flavor |
| 发布渠道 | 侧载（夸克网盘 + share 域名） | 不上架商店 |
| ABI | ARM64 为主 | 资产全为 `-arm64` / `aarch64` |

### 3.2 两条硬约束（不可协商）

**① 包名必须恰好 15 字符**

Termux 官方二进制把 `/data/data/com.termux/files`（27 字节）烤进 ELF 的 `.dynstr`，
`TermuxBootstrap.patchElfInPlace()` 只能做**等长原地覆盖**：
替换串 `/data/data/<包名>/` = 12 + N 字节，等于 27 ⇒ **N = 15**。

长度不等时该函数 `return 0` **静默跳过**，症状是 `CANNOT LINK EXECUTABLE`。

**② targetSdk 必须 ≤ 28**

Android 10（API 29）起，targetSdk ≥ 29 的应用不允许 `execve()` 自身私有目录里的文件
（W^X / SELinux `untrusted_app` 域禁止 `app_data_file execute_no_trans`），
而 node / bash / dpkg 全装在 `filesDir` 下 —— 一升级就全线 Permission denied。

**代价**：只能侧载。

> 目的：让 G1 阶段知道「现有代码哪些能复用、哪些要改」。

| 文档要求 | 当前实现 | 差距 |
|---|---|---|
| 双内核（一号 A/R、二号 E） | 单内核 + L1/L2/L3 三级降级 | 🔴 架构级差异 |

| 体检在**诊断副本**上跑 `--dump-config` | `preflight()` **直接在原 A 上跑**（`DSH_HOME` 指向 `dshHome`） | 🔴 **违反文档 §6.2**，见 §6.1 |
| flock 绑定 | ✅ 已有（预编译资产 + 平台白名单补丁） | ✅ 可复用 |
| PTY | ✅ 已有（node-pty android-arm64） | ✅ 可复用 |
| targetSdk 28 / 包名 15 字符 | ✅ 已满足 | ✅ 可复用 |

### 6.1 🔴 重要发现：现有体检违反文档要求

设计说明 §6.2 明确要求：

> 锁定版本会调用 `prepareProfile`，并可能**重写 profile 配置、规范化 manifest
> 或清理链接**，因此**不得直接在原 A 上**把它当只读命令运行。先确认停写并
> 复制完整受测布局到诊断副本，在副本运行，记录规范化差异并验证原 A
> 哈希/元数据未变。

**现有实现直接违反**。证据（`EngineManager.kt` L6568-6582）：

```kotlin
private fun runDumpConfig(): DumpResult? {
    ...
    pb.environment().apply {
        put("DSH_HOME", dshHome.absolutePath)   // ← 就是原 A
        put("HOME", homeDir.absolutePath)       // ← 也是原 A 的 home
    }
}
```

`preflight()` 在 L4966 和 L5013 各调一次，两次都跑在原 A 上。

**实际风险**：如果 `prepareProfile()` 确实会重写 profile（文档说的），那每次启动
的体检都在**改动用户配置**。这与「体检对原 A 保持只读」直接冲突。

**这条需要单独验证**：`--dump-config` 在当前锁定的引擎版本上到底会不会写盘。
验证方法：跑前跑后比对 `profiles/web/` 的文件哈希。

**修复方向**（G3 阶段）：
1. 先验证是否真的会写（也许当前版本不会，那风险就只是「未来版本可能」）
2. 若会写 → 改为在临时副本上跑（复制 `profiles/` 到 `cache/` 下）
3. 记录规范化差异，验证原 A 未变

## 9. G0-02 补充：构建可复现性验证

> 本节是 G0-01 盘点过程中顺带完成的 G0-02 核心验收项。

### 9.1 验证方法

用**全新的 `GRADLE_USER_HOME`**（空目录，只放 `gradle.properties`）重新构建，
等价于「换一台机器、没有缓存」的场景：

```bash
export GRADLE_USER_HOME=/tmp/clean-gradle-home   # 空目录
./gradlew :app:assembleSystemDebug
```

### 9.2 结果

| 项 | 值 |
|---|---|
| 构建耗时 | **3 分 23 秒**（含下载全部依赖） |
| 下载缓存 | 1.1 GB |
| 构建结果 | `BUILD SUCCESSFUL`，37 tasks |
| **产物哈希** | `511800c68bf7480898760bdd1f8abc29…` |
| **与增量构建对比** | **完全一致** |

### 9.3 结论

✅ **构建是字节级可复现的** —— 全新缓存与增量缓存的产物 sha256 完全相同。

这满足 G0-02 的验收条件「干净环境可按锁定步骤构建」中的**可复现**部分。

### 9.4 但「干净环境」有一个前提要说清

`./gradlew clean` **只清项目 `build/` 目录，不清 Gradle 全局缓存**
（`$GRADLE_USER_HOME`，本机 3.9 GB）。所以：

| 操作 | 耗时 | 是否算「干净构建」 |
|---|---|---|
| `./gradlew clean && assemble` | 8 秒 | ❌ 缓存还在，37 tasks 全 up-to-date |
| 换 `GRADLE_USER_HOME` + assemble | 3分23秒 | ✅ 真正重新下载与编译 |

**做可复现性验证时必须用后者**，否则会被 8 秒的假象误导。
