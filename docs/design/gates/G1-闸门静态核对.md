# G1 四个路线闸门的静态核对

> 阶段：G1（单 A 跑通，并裁决四个路线闸门）
> 日期：2026-10-22
> 状态：**静态核对完成；动态验证（真机）待用户配合**

---

## 0. 本文件能证明什么、不能证明什么

开发指导 §G1 要求「分别给四个路线闸门结论」。四个闸门都需要**真机动态验证**，
而本机是 Linux 服务器、无 Android 设备连接。

所以本文件只做**静态核对**——从代码与资产里确认「前提条件成立」，
**不能替代真机验证**。每条都标注了「还需要什么证据」。

---

## 1. 闸门一：平台兼容

> 通过条件：真机运行真实文件锁、PTY、子代理和原生绑定；不禁用互斥、不改禁止语义。

### 1.1 文件锁（flock）

| 项 | 状态 | 证据 |
|---|---|---|
| 原生绑定存在 | ✅ | `app/src/main/assets/node-addon-system-android-arm64.zip` |
| 平台白名单补丁 | ✅ | `ensureSystemAddon()` 把 `flock.js` 的白名单补上 `android` |
| 源码来源 | ✅ | 官方 `src/flock.c`，**未修改**，用 NDK 编译 |
| 绑定格式 | ✅ | `bin/system.node`，与官方平台包结构一致 |

**代码依据**（`EngineManager.kt` L670-700）：

> 该插件的 `lib/flock.js` 只白名单了 linux/darwin…Android 上 `process.platform === 'android'`，
> 于是直接抛 `ERR_FLOCK_UNSUPPORTED_PLATFORM`。但 bionic 的 `sys/file.h` 里就有
> `int flock(int, int)`，Android 是支持 flock(2) 的。

**⚠️ 待验证**：真机上 `SessionWriteLease.acquire()` 能否真的拿到锁、并发写者是否互斥。

### 1.2 PTY

| 项 | 状态 | 证据 |
|---|---|---|
| 原生绑定存在 | ✅ | `app/src/main/assets/node-pty-android-arm64.zip` |
| 安装逻辑 | ✅ | `ensureNodePty()` |
| 用途 | — | `dsh-subprocess-local` 的终端后端走 `node-pty` |

**⚠️ 待验证**：真机上 PTY 输入/resize/断线重连。

### 1.3 子代理 / 后台任务

| 项 | 状态 | 证据 |
|---|---|---|
| 引擎自带 | ✅ | `dsh-tool-subagent`、`dsh-tool-jobs`、`dsh-tool-ralph` 在引擎包里 |

**⚠️ 待验证**：真机上子代理启动、后台任务、遗留后代清理。

### 1.4 闸门一结论

**静态：前提成立**（三个原生绑定都在，且来源合法）。
**动态：未验证** —— 需真机。

## 2. 闸门二：安全表达

> 通过条件：不虚报完整隔离；不能准确表达则适配或阻断，不静默全权。

### 2.1 现有声明

`docs/agents/sandbox.md` 与代码注释里对 sandbox 的定位是**合作式约束**，不是内核级沙箱。

**证据**（设计说明 §4 也这么要求）：

> 保留审批、拒绝反馈和权限模式；**真实报告合作式限制**，
> 不把 LD_PRELOAD 等用户态拦截报告为完整内核沙箱。

### 2.2 组件清单

| 组件 | 类型 | 是否如实声明 |
|---|---|---|
| `libboosandbox.so` | LD_PRELOAD 拦截 | ⚠️ 需核对文档是否声明为「合作式」 |
| `boo-sandbox-run` | 子进程 runner | 同上 |
| `liblinkcompat.so` | link 兼容层 | 同上 |

**⚠️ 待核对**：这三者在用户可见的地方（设置页、工具描述、错误信息）
是否被表述为「完整沙箱」。若被夸大，则闸门二不通过。

### 2.3 闸门二结论

**静态：未完成核对** —— 需要逐条检查用户可见文案。
**动态：未验证** —— 需真机做「允许/拒绝/拒绝反馈/审批模式」成套实验。

## 3. 闸门三：发行执行

> 通过条件：真实设备通过；包名/ELF 前缀、ARM64 载荷、targetSdk 28 的安装与执行。

### 3.1 包名与 ELF 前缀（硬约束①）

**实测验证**：

```
OLD_TERMUX_ROOT   = "/data/data/com.termux/files"    27 字节
elfRootReplacement = "/data/data/com.dsh.android/"    27 字节
```

✅ **等长** —— `patchElfInPlace()` 的 `old.size != new.size` 守卫不会触发。

代码里还有一道 `check()`（L949）在启动时断言等长，不等长会**直接抛异常**而不是静默跳过。
这是好事（比静默失败容易发现），但也意味着改包名会让 App 立刻崩 —— 符合文档「硬约束」的定位。

### 3.2 targetSdk（硬约束②）

| 项 | 值 | 依据 |
|---|---|---|
| targetSdk | **28** | `app/build.gradle.kts` L34 |
| minSdk | 26 | 同上 |
| compileSdk | 35 | 同上 |

✅ 满足「≤28」要求。

### 3.3 ARM64 载荷

| 资产 | ABI |
|---|---|
| `bootstrap-aarch64.zip` | aarch64 |
| `node-runtime.bin` | ARM aarch64（`file bin/node` 实测） |
| `node-pty-android-arm64.zip` | arm64 |
| `node-addon-system-android-arm64.zip` | arm64 |
| `pnpm-android-arm64.zip` | arm64 |
| `ripgrep-android-arm64.zip` | arm64 |

✅ 全部为 ARM64，无 x86 混入。

### 3.4 闸门三结论

**静态：三项硬条件全部满足**（包名 15 字符且 ELF 等长、targetSdk 28、全 ARM64）。
**动态：未验证** —— 需真机确认安装与二进制执行。

## 4. 闸门四：管理协调

> 通过条件：无并发写入、可确认停止；无法确认时拒绝，不假定官方天然参加监督锁。

### 4.1 现状

**🔴 这是四个闸门里唯一「完全没有实现」的。**

现有代码里没有任何「单写者」「维护窗口」「停写确认」机制。

相关但不等价的现有机制：

| 现有 | 为什么不等价 |
|---|---|
| `enterSafeMode()` 会 `stop()` 引擎 | 是「停止后改」，不是「确认没有并发写者」 |
| `preflight()` 跑 `--dump-config` | 直接在原 A 上跑，没有停写确认 |

### 4.2 设计说明的要求

§6.5.1「资产归属与写入表」要求每个资产有明确的「管理者与允许写者」、
「版本与一致性边界」、「快照及清理规则」。这是全新的设计。

§5.3.4 的「可靠首版流程」明确：

> 登记管理事务 → 冻结管理入口 → 等待/确认停止写者 → 停 A 并确认后代/代理状态
> → 在私有区取得一致快照 → 恢复原组合与页面 → 对快照流式压缩加密
> → SAF 验证发布 → 三份轮换

### 4.3 闸门四结论

**静态：未实现**。
**动态：不适用**（没有可验证的对象）。

**这是进入 G2 之前必须先做的** —— 因为 G2（监督器与完整救援闭包）依赖「能确认停写」。
