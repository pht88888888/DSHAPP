## 2. 实现

`app/src/main/java/com/dsh/android/manage/ManageLock.kt`

### 2.1 为什么用 `FileChannel.tryLock()`

| 方案 | 跨进程 | 崩溃后自动释放 | Android 可用 |
|---|---|---|---|
| `synchronized` / `ReentrantLock` | ❌ 只在本 JVM | — | ✅ |
| **`FileChannel.tryLock()`** | ✅ | ✅（fcntl 语义） | ✅ |
| 自建 pid 文件 | ✅ | ❌ 需手工清理 | ✅ |

**决定性的一条是「崩溃后自动释放」**：崩溃循环是这个 App 最常见的故障形态，
自建 pid 文件在那种场景下会留下永久死锁，用户只能清数据。

机制照抄项目内已有的两处（`TermuxBootstrap.withPrefixFileLock`、
`LogUploader` 的补传锁）—— 同一手法已跑过真机。

### 2.2 三个设计要点

**① `OverlappingFileLockException` ≠ 另一个进程**

同一个 JVM 内对同一文件重复加锁会抛这个异常，与「另一进程持锁」是两件事。
代码里分成 `HeldByThisProcess` / `HeldByOtherProcess` 两种结果，
日志如实区分 —— 否则排查时会往「进程重叠」方向查，而实际只是同进程重入。

**② 锁文件放 `filesDir/manage/`，不放 `cache/`**

`cache/` 会被系统回收，那样两个进程可能各自创建一份新文件、各自加锁成功，
锁就失效了。

**③ 持锁期间不做长耗时操作**

锁是**管理操作**的互斥，不是「引擎运行期间一直持有」。启动拿到锁、
完成状态转换后立刻释放，否则修复/停止会被一直挡住。

## 3. 验证（真实 JVM，非模拟）

### 3.1 测试方法

用独立 Java 程序模拟两个进程争抢同一个锁文件：

```java
RandomAccessFile raf = new RandomAccessFile("/tmp/locktest/manage.lock", "rw");
FileLock l = raf.getChannel().tryLock();
```

### 3.2 结果

| 测试 | 预期 | 实际 |
|---|---|---|
| 单进程获取 | ACQUIRED | ✅ ACQUIRED |
| A 持锁时 B 尝试 | BLOCKED | ✅ BLOCKED-BY-OTHER |
| A 释放后 B 获取 | ACQUIRED | ✅ ACQUIRED |
| **A 被 `kill -9` 后 B 获取** | **ACQUIRED（不死锁）** | ✅ **ACQUIRED** |

第 4 条是最关键的：崩溃场景下锁自动释放，不会留下死锁。

### 3.3 这证明了什么、没证明什么

**证明**：`FileChannel.tryLock()` 的跨进程互斥与崩溃释放语义在真实 JVM 上成立。

**没证明**：
- 未在 **Android 真机**上验证（Linux JVM 与 ART 的 fcntl 实现理论上一致，但未实测）
- 未验证 SELinux 策略对锁文件的影响
- 未接入 `EngineManager`（当前只是独立工具类）

## 5. 第二块：ManageState（持久状态）

`app/src/main/java/com/dsh/android/manage/ManageState.kt`

### 5.1 解决什么

没有它的话，App 被杀在切换中途时，下次启动**无从判断**上次做到哪一步 ——
只能猜，而猜错的代价是「两个环境同时被当成激活态」或「修复时旧写者还在写」。

### 5.2 三个核心概念

| 概念 | 含义 | 为什么 |
|---|---|---|
| `epoch` | 管理代次，每次转换 +1 | 旧 epoch 的请求必须被拒，否则切换后旧的异步回调还能改状态 |
| `transitionId` | 一次转换的唯一 ID | 崩溃后靠它判断「同一次转换的续做，还是新的一次」 |
| `desired`/`observed` | 想要的状态 / 实际观察到的 | 两者不一致 = 转换未完成，恢复时要对账 |

### 5.3 验证（真实 `/proc`）

| 测试 | 结果 |
|---|---|
| `starttime` 字段索引 | ✅ 索引 19，算出进程已运行 0.1 秒（错位会得荒谬值） |
| PID 相同 + starttime 不同 | ✅ 判定为「不是同一进程」（PID 复用） |
| PID 与 starttime 都相同 | ✅ 判定为「同一进程」 |

### 5.4 如实承认的边界

只做到「写临时文件 → `fsync` → `rename`」。目录项 fsync 在 Android 上会
EACCES（见 `patchAttachmentDurability`），所以：

- ✅ 能防**进程被杀**
- ❌ 不能完全防**断电**

文档明确说「仅写 JSON 或改名不能自动证明断电一致性」，这里如实照做能做的部分，
不夸大保证。

### 6.0 冻结闸门（第四块）

设计说明要求「切换前**冻结新管理写入**…**再**请求停止」——顺序是硬性的。

`ManageGate` 解决「用户点备份时 AI 正在写文件」这个场景：先把新请求挡在
门外，让在飞的写完，再取快照。

两个关键设计：

- **不可抢占**：已有冻结时返回 false 不覆盖。覆盖会让先发起的流程失去保护。
- **刻意不持久化**：冻结是运行时概念，进程死了自然失效。持久化会制造
  「上次冻结没解除」的幽灵状态。

接入顺序（实测验证）：

```
requestStop()     → freeze(SWITCHING) → beginTransition
confirmStopped()  → 确认停止后才 unfreeze
```

⚠️ 解冻位置很关键：放在 requestStop 之后会让「停止还没确认」的窗口失去
保护，而那正是引擎可能还在写的时候。边界已验证——停止失败时保持冻结。

### 6.0.1 如实承认的边界

设计说明自己说了：「epoch 仅约束**经过网关的请求**，**不阻止仍在运行的
任意代码直接写文件**」。

所以 `ManageGate` 是**合作式约束**，不是安全边界：

- ✅ 挡得住：通过 `canProceed()` / `withFreeze()` 发起的管理请求
- ❌ 挡不住：AI 通过 `bash` 直接写文件、插件异步回调、其他进程

与项目对 sandbox 的定位一致（`docs/agents/sandbox.md`：不把 LD_PRELOAD
报告为完整沙箱）。

### 6.1 状态机实现过程中发现的三个真实缺陷

这三个都是先写逻辑、再用等价复现推演时暴露的，**编译发现不了**：

**① `descendantsGone=null` 会导致永久死锁**

原实现把「无法确认子进程」也当拒绝。而 Android 上引擎的子进程（node 拉起的
bash/pnpm）没有可靠的进程组归属可查 ⇒ 每次正常 `stop()` 都得到 `null`
⇒ 停在 QUIESCING ⇒ 下次 `start()` 被拒 ⇒ **App 再也起不来**。

修正：只有**确认还在**（`false`）才拒绝；`null` 放行并记事件。
Android 上「查不到」是平台常态，一律拒绝等于把平台限制变成功能故障。

**② `confirmStopped` 推进到 `STARTING` 是错的**

`STARTING` 语义是「进程已拉起、还没就绪」，停止完成后进程是**没有**的。
推进到它会让下次 `start()` 判为「上次未完成」。修正：推进到 `IDLE`。

**③ 初始 `observed=null` 让首次启动被拒**

`isInFlight()` 判据是 `desired != observed`，`null != A` 为真 ⇒ 全新安装被
判成「上次转换未完成」。修正：初始 `observed=A`。

后者要等状态机全流程做完再谈。
