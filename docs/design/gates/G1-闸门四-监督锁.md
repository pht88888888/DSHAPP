## 2. 实现

`app/src/main/java/com/dsh/android/manage/ManageLock.kt`

### 2.1 为什么用 `FileChannel.tryLock()`

| 方案 | 跨进程 | 崩溃后自动释放 | Android 可用 |
|---|---|---|---|
| `synchronized` / `ReentrantLock` | ❌ 只在本 JVM | — | ✅ |
| **`FileChannel.tryLock()`** | ✅ | ✅（fcntl 语义） | ✅ |
| 自建 pid 文件 | ✅ | ❌ 需手工清理 | ✅ |

**决定性的一条是「崩溃后自动释放」**：崩溃循环是这个 App 最常见的故障形态，
自建 pid 文件在那种场景下会留下永久死锁，用户只能清数据。

机制照抄项目内已有的两处（`TermuxBootstrap.withPrefixFileLock`、
`LogUploader` 的补传锁）—— 同一手法已跑过真机。

### 2.2 三个设计要点

**① `OverlappingFileLockException` ≠ 另一个进程**

同一个 JVM 内对同一文件重复加锁会抛这个异常，与「另一进程持锁」是两件事。
代码里分成 `HeldByThisProcess` / `HeldByOtherProcess` 两种结果，
日志如实区分 —— 否则排查时会往「进程重叠」方向查，而实际只是同进程重入。

**② 锁文件放 `filesDir/manage/`，不放 `cache/`**

`cache/` 会被系统回收，那样两个进程可能各自创建一份新文件、各自加锁成功，
锁就失效了。

**③ 持锁期间不做长耗时操作**

锁是**管理操作**的互斥，不是「引擎运行期间一直持有」。启动拿到锁、
完成状态转换后立刻释放，否则修复/停止会被一直挡住。

## 3. 验证（真实 JVM，非模拟）

### 3.1 测试方法

用独立 Java 程序模拟两个进程争抢同一个锁文件：

```java
RandomAccessFile raf = new RandomAccessFile("/tmp/locktest/manage.lock", "rw");
FileLock l = raf.getChannel().tryLock();
```

### 3.2 结果

| 测试 | 预期 | 实际 |
|---|---|---|
| 单进程获取 | ACQUIRED | ✅ ACQUIRED |
| A 持锁时 B 尝试 | BLOCKED | ✅ BLOCKED-BY-OTHER |
| A 释放后 B 获取 | ACQUIRED | ✅ ACQUIRED |
| **A 被 `kill -9` 后 B 获取** | **ACQUIRED（不死锁）** | ✅ **ACQUIRED** |

第 4 条是最关键的：崩溃场景下锁自动释放，不会留下死锁。

### 3.3 这证明了什么、没证明什么

**证明**：`FileChannel.tryLock()` 的跨进程互斥与崩溃释放语义在真实 JVM 上成立。

**没证明**：
- 未在 **Android 真机**上验证（Linux JVM 与 ART 的 fcntl 实现理论上一致，但未实测）
- 未验证 SELinux 策略对锁文件的影响
- 未接入 `EngineManager`（当前只是独立工具类）
