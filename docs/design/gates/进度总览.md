### G2 第四轮补充：E 环境独立依赖树 ✅

新增 `EmergencyEnv`（独立目录 + 版本戳 + 空间检查 + 两段式部署）。

**为什么 E 必须预先解包**（文档 §6.5.4「不能依赖故障发生后才解包」）：

| 场景 | 事后解包会怎样 |
|---|---|
| 磁盘快满 | 解到一半 ENOSPC，半成品比没有更糟 |
| engine.bin 损坏 | 解包失败，E 也起不来 |
| 用户急着救数据 | 要等 15 秒 + 可能失败 |

所以在**正常启动成功后异步部署**（不在启动路径上，否则每次启动多等十几秒）。

**磁盘代价如实标注**：独立依赖树 = 再解包约 120~160 MB。
`shouldDeploy()` 有三条拒绝条件，空间不足（<350MB）时**不部署并如实报状态**，
不硬塞把用户磁盘占满。

**部署顺序的安全性**：`写 staging → 旧 E 改名 .old → staging 改名 E → 删 .old`。
不是「先删再放」——那样断电会两头落空。实测验证：就位失败时旧 E 保住
（stamp 仍是旧值），移开失败时无损。

**启动决策**：`shouldLaunch()` 关键一条是「**一号健康时不切 E**」——
E 是最后一道门，不是更好的选择。切过去会丢用户当前会话与正在跑的任务。

### G2 第五轮补充：完整恢复链 ✅

新增 `RecoveryChain`（A→R→E→原生恢复页）+ `RescueBoot.Tier.EMERGENCY`。

**解决两个核心问题**：

**① 无限重启** —— 现有降级是「失败就往下退一格」，但退到底之后没有出口，
会变成「E 起不来 → 重启 → 还是 E → …」。文档明确禁止。现在能判出 GIVE_UP
并**不启动引擎**，直接进原生恢复页。

**② 不重置 A** —— 文档：「留在 R 诊断 A，不重置 A」。决策器只决定去哪，
不做任何修改。

**关键细节**：

- 一号不可用时**跳过 R 直接进 E**：R 用的还是一号内核代码，一号文件坏了
  R 必然也起不来，硬试只是白等 15 秒
- 用 `emergencyJustTried` 而非 `tier == EMERGENCY` 判无限重启：tier 是持久化的，
  光看它会导致每次启动都 GIVE_UP，用户连手动重试的机会都没有
- R 记录但本次未试 → 再试一次（用户可能刚修好）

**加枚举值后编译器逼着补了 3 处 when 分支**，每处文案都强调性质区别：
救援/安全模式是「同一套内核换配置」，应急模式是「**换了内核**」——
排查方向完全相反。

| 组件 | 职责 | 验证 |
|---|---|---|
| `BackupCrypto` | PBKDF2 + AES-GCM 分段 + HMAC 整包 | **6 场景**：往返/错密码/篡改/截断/重排/头部篡改 |
| `BackupBundle` | 目录↔明文 zip 流、解压炸弹防护 | 编译验证 |
| `BackupManifest` | 清单（加密在包内，不进明文头） | — |
| `BackupRotation` | 三份轮换、失败包不挤占 | **7 场景** |
| `BackupPublisher` | SAF 写入 + 读回验证 | 编译验证 |
| `BackupScheduler` | eventId 去重、防备份风暴 | **6 场景** |
| `BackupOrchestrator` | 串起完整流程 | 编译验证 |

**密码学选型**：复用 JDK 标准实现（文档要求「不自创算法」），无第三方依赖。
PBKDF2 210k 迭代实测 1551 ms；内存恒定（流式）。

**最关键的两个验证**：

1. **加密容器 6 项全过** —— 特别是「段重排」和「截断」，
   这两项是分段 GCM 单独做不到的，靠末尾 HMAC 兜住
2. **防备份风暴** —— 模拟「用户打开 1 次 + 维护续启 5 次」，
   总共只触发 1 次备份（否则会无限循环填满用户磁盘）

### G4 第二轮补充：端到端打通 ✅

| 新增 | 内容 |
|---|---|
| `BackupConfig` | 密码 Keystore 包裹（**不存明文**）、SAF URI、开关 |
| 原生桥 5 方法 | status / setPassword / chooseDir / setAutoEnabled / runNow |
| 设置页「备份与恢复」 | 状态、设密码、选目录、开关、立即备份、5 条说明 |
| 自动备份接入 | 引擎就绪登记 → onUiReady 后延迟 30s 执行 |

**关键设计**：

- Keystore 密钥**不可导出** ⇒ 拿到密文换台设备也解不开。
  备份包本身的加密用**用户密码**，所以重装后输密码仍能解密 ——
  Keystore 丢了只影响「自动备份要不要重新输密码」。这正是文档要的
  「不能用 Android Keystore 代替可跨设备输入的密码」。
- `backupRunNow()` **只代表受理，不代表成功**（成功看 lastSuccessAt）——
  把「已受理」说成「成功」会让用户以为有备份，实际可能失败在加密阶段。
- 自动备份用 `onUiReady` 而非「引擎就绪」：后者只说明服务起来了，
  页面可能还是白的；此时停引擎备份，用户看到「刚打开就卡住」。

### G3 第二轮：事务状态机 + 锁顺序 ✅

**`UpdateTransaction`**（433 行）：五阶段提交，单一可判定提交点。

设计说明要求「**不各写一个互不相关的『当前版本』**」——做法是让激活记录
（`Active`）成为唯一真相源，只有一个字段决定用哪套组合：

```
active == "candidate" ⇒ 新组合；否则旧组合
```

**没有第三种可能**，所以「无法判定」在构造上不可能发生。

两个关键设计：

- **提交点必须一次写入**：`commit()` 同时改 phase 与 active。分两次写的话，
  崩在中间会得到「判定为未提交，但候选已部分接管」的矛盾状态。
- **判定用 active 而非 phase**：phase 可能停在 COMMITTING，而 active 一旦是
  CANDIDATE 就意味着「候选已该接管」。active 是**承诺**，phase 只是**进度**。

验证 7 个崩溃点全部判定正确；提交后与未提交的状态集**无交集**（无歧义）。

**`ManageLockOrder`**（206 行）：监督锁 → 环境锁 → 发布锁固定顺序。

死锁分析：若允许任意顺序，`T1: 拿监督锁等环境锁 / T2: 拿环境锁等监督锁`
立刻死锁。只允许 1→2→3 递增后，循环等待在**构造上**不可能。

第二条规则更隐蔽：「**禁止边持锁等待用户无限输入**」——持锁弹对话框、
用户去吃饭、整个管理面卡住且没有报错。

### G4 第三轮：导入端到端 ✅

新增 `BackupImporter`（三步分离）+ 4 个桥方法 + 设置页导入区。

**三步分离**（安全的关键）：

```
① inspect()  只读：解开头部 + 密码验证 + 出清单   ← 不改任何东西
② stage()    解到私有暂存区并逐文件校验            ← 只写 cache
③ apply()    建恢复点 → 替换 → 失败可回滚          ← 唯一动 A 的一步
```

用户在 ① 之后能看到「这个包是什么、会覆盖什么」再决定。

**实现过程中修掉一个数据丢失级缺陷**：

第一版无条件把全部目录移进恢复点，于是「备份里没有 skills、当前有 skills」时：
skills 被移走 → 因为没源而不复制 → 恢复点被删 → **用户 skills 永久丢失**。
实测验证暴露了它。修复后只移走「备份里确实有」的目录。

### G4 第四轮：profile 恢复 + 依赖一致性 ✅

**问题**：备份纳入了 `profiles/web/{package.json, cordis.patch.yml}`，
但恢复只处理 5 个目录，**不含 profile** —— 「备份了配置但恢复不回来」。

**修法：逐文件恢复，不整体替换目录**。⚠️ 不能整体替换 `profiles/web/`：
那目录里还有 `node_modules`（几百 MB），整体替换会把用户的插件安装状态
换成备份时的（可能已过期），且导入时间从秒级变分钟级。

**依赖一致性校验**：文档要求「不盲目混合两套依赖图」。真实场景是
备份的 `bundles` 清单里有某插件，但包实体没进备份（可从 npm 重装），
恢复后「清单说启用 X 但 X 没装」—— 引擎报错只指向包名，用户不知道
这是「导入了一份来自别的机器的备份」导致的。

⚠️ **只提示不自动修改**：自动摘条目会改变用户的插件配置，必须是显式动作。

验证：正常恢复（配置换成备份版、**node_modules 保住**）、中途失败回滚
（配置恢复成当前版、node_modules 保住）。备份↔恢复**完全对称**。

## 六点八、G5 第一块：LayoutAdapter ✅

设计说明 §4.9 要求「原生窗口处理 + **单一布局适配器** + 局部界面增强」三层结构。

**精确阈值**（文档原文，用整数交叉相乘避免浮点误差）：

| 条件 | 布局 |
|---|---|
| 手动 mobile / official | 锁定 |
| auto 且 r > 4/3 | official |
| auto 且 r < 3/4 | mobile |
| auto 且 **3/4 ≤ r ≤ 4/3** | **保留上次；初次 mobile** |

**为什么必须换掉现有实现**——现有 `client.js` 用 `innerWidth < 1024` +
「非桌面指针」，文档逐条否定了：

| 现有做法 | 文档要求 | 后果 |
|---|---|---|
| 宽度阈值 | **宽高比** | 分屏变窄但仍是宽屏比例，误判 |
| 无滞回 | **3/4~4/3 保留上次** | 阈值附近抖动导致布局横跳 |
| 看指针类型 | **不看鼠标** | 平板接鼠标突然变桌面布局 |

**滞回实测**：窗口从 r=1.343 缩到 1.204，布局一直保持 official 不切换。

**原生侧的关键细节**：高度必须**不含 IME** —— 文档明确「不用键盘缩小后的
visualViewport 误判方向」。用 `WindowMetrics` + `getInsetsIgnoringVisibility`
而不是 visualViewport。

**不重建 Activity**：`configChanges` 已含旋转/分屏，布局变化用
`evaluateJavascript` 推事件而非 `loadUrl`（重载会丢草稿）。

### G5 第二轮：前端接入（判据归一）✅

之前 LayoutAdapter 能算了，但前端还在用旧的 `innerWidth < 1024` + 指针判断 ——
**两个布局执行者**，正是文档禁止的。

`mpIsMobile()` 是唯一入口（40 处调用），只改它的判据来源：

```
① 读 window.__DSH_LAYOUT__（原生算好的）
② 没有 → 退回旧的宽度+指针判据（降级）
```

`data-mobile` 由 `mpSyncMobileAttr()` 统一维护，控制所有 CSS 作用域 ——
改一个函数同时改 CSS 与 JS，不会判据不一致。

**两个关键细节**：

- **初始化必须主动拉一次**：原生可能在页面加载**之前**就推送过布局，
  那次推送发生在还没有监听器时，等于丢了。不主动拉的话首屏会用降级判据
  建出错误界面再被修正，用户看到闪一下。
- **`dsh-layout-changed` 与 `resize` 并存但不是冗余**：后者每次尺寸变化都触发，
  前者只在**实际布局切换**时触发（因为有滞回）。「布局没变但尺寸变了」时
  前者会触发重建（闪烁），后者不会。

验证判据优先级 7/7：原生 mobile + 宽屏 → mobile（原生说了算）；
无标志 + 窄屏 + 有鼠标 → official（桌面缩窗不受影响）。

### G5 第三轮：布局设置 UI ✅

上一轮桥就绪了但用户没地方改，本轮补上设置入口。

⚠️ 文档「**设置所有者与布局执行者分开**」：本节只保存偏好，
实际布局由原生 LayoutAdapter 决定，**从不自己算**。

UI 含：当前设置值 + **实际布局**（两者分开显示，用户能看到「我设的是 auto，
实际用的是手机布局」）、三个模式按钮、自动模式的三条规则、三条注意事项。

**为什么把规则写进 UI**：用户看到「横过来还是手机布局」时最需要知道规则本身。
滞回区间（3/4~4/3 保留上次）如果不解释，用户会以为坏了 —— 而实际是刻意设计。

### G5 第四轮：四类清理 ✅

文档要求「清理**样式、监听、观察器与借用控件**」。

盘点「进入时创建」vs「退出时清理」发现三处真实缺陷：

|---|---|---|
| `mpCloseTimer` | 未清理 | 拆解时若还在飞，回调会点官方 toggle —— **退出移动布局后侧栏莫名折叠一次** |

## 六点九、G6 第一块：悬浮事件闸门 ✅

设计说明 §4.11：「不采用**无规则的最后写入覆盖**」「切换环境时撤销旧租约…
不得继续显示旧任务正在运行」。验收矩阵第 18 条：「**乱序或过期事件不覆盖当前状态**」。

**要解决的真实问题**：悬浮窗状态由多来源并发更新（页面桥、引擎插件、物理 tick、
状态轮询）。没有序号时会「任务明明结束了，球还在转」——因为迟到的旧事件
在 UI 层覆盖了新状态。

**解法两层**：

- **序号**解决同环境乱序：只接受严格大于当前的
- **租约**解决跨环境迟到：环境 A 的 seq=5 在切到 R（seq 归零）后到达，
  `5 > 0` 本会被接受，但租约不符一律丢弃

**接入点很关键**：在 `applyAppearance()` 拦（唯一配置入口），能把旧事件挡在
**落盘之前** —— 落到磁盘再拦就晚了，下次启动会读到它。

`_seq`/`_lease` 是**可选** JSON 字段，不带时视为「当前租约+下一序号」，
不破坏现有调用方。

验证 5 场景全过，含两个关键：旧状态迟到 → StaleSeq 丢弃；
跨环境迟到 → StaleLease 丢弃。

### G6 第二轮：会话聚合 + 插件仲裁 ✅

**`SessionAggregator`**（209 行）：验收矩阵第 18 条要求「多会话事件有
**明确跟随/聚合规则**」。

问题：引擎可同时跑多个会话，而悬浮窗只有一个显示位。现有实现接受单一状态，
多个会话互相覆盖 —— 用户看到球乱跳，而**实际上有个会话一直在等他确认**。

聚合规则：**等待确认(1) > 干活中(2) > 思考中(3) > 空闲(4)**，
同优先级按**最近活跃**（用户关心「刚在动的那个」，不是字母序靠前的）。

**`PluginArbiter`**（237 行）：§4.11「不采用**无规则的最后写入覆盖**」
「插件重启**不能无条件覆盖用户后续修改**」。

仲裁规则：**用户手动 > 先注册的插件 > 未注册来源**。

⚠️ 「先注册赢」而不是「后注册赢」：后者等价于最后写入覆盖，文档明确禁止。
用户想让后来的赢就去设置页手动改（显式动作）。

**按字段锁定而非整体**：用户可能只想固定颜色、让插件继续控制动作。
整体锁定会废掉插件主要功能。

验证 12 场景全过，含「用户接管后插件抢不回」「锁定 color 后插件改 color 被拒
但改 action 允许」「换环境清空控制权但保留用户锁定」。

### G6 第三轮：sessionId 贯通 ✅

上一轮写好了聚合器，但 `EngineStatus` 没有 sessionId 字段 ——
**聚合器拿不到真实的多会话数据，等于空转**。本轮打通三段：

| 段 | 改动 |
|---|---|
| 页面侧 | `mpCollectStatus()` 加 `sessionId`，取 `sessions.list.getSnapshot().current` |
| Kotlin 侧 | `EngineStatus` 加 `sessionId: String = ""`（默认参数，不破坏现有构造点） |
| 悬浮窗侧 | `syncRunState()` 改成先喂聚合器再选代表（原来是最后写入者赢） |

⚠️ **一个关键的空值处理**：`sessionId` 为空时**照旧走单状态路径**，不塞进聚合器。
空串意味着页面拿不到当前会话（首帧、官方 DOM 变了、旧版页面），
硬塞进去会让「无归属状态」参与竞争，**反而把真实会话的状态挤掉**。

验证：A 在等确认时来了一个空 ID 的「干活」状态，显示走单状态路径，
但聚合器里 A 仍是 waiting ✅ 没被污染。

### G6 第四轮：持久化 + 生命周期 + 字段清单 ✅

**① 用户锁定持久化**：「重置语义明确」的前提是**记得住**。不持久化的话
用户锁了颜色 → 重启 → 锁定没了 → 插件立刻改回去 → 用户觉得「设置没用」。

**② 插件生命周期钩子**：文档「插件停止/卸载时立即撤销运行控制」。
两条路径都要有 —— 正常卸载走 `release()`，崩溃/强杀只能靠 `sweepDeadOwners()`。

⚠️ `sweepDeadOwners()` 用**回调注入**存活判定，不直接依赖插件管理器，
避免循环依赖。用户持有不清扫（用户不会「死掉」）。

**③ `BubbleFieldNames`**：桥需要「列出所有可锁定字段」，各抄一份迟早与
`merge()` 漂开 —— 症状是「锁了字段但没生效」，排查时看不出原因。

**校验：merge 80 个字段 vs ALL 80 个，完全一致 ✅**
（⚠️ 这个校验是手工跑的脚本，新增字段时两处都要改）

### G6 第五轮：媒体 WebView 安全加固 ✅

文档：「媒体 WebView **只加载受管内容，不开放任意网页或插件脚本执行口**；
**隐藏/锁屏/节能暂停无用解码与循环**」。

**审计发现 7 项安全设置一个都没配**，全依赖默认值。其中两条默认值在旧 API
上是**开**的：

| 设置 | 风险 |
|---|---|
| `allowFileAccessFromFileURLs` | file:// 页面可读其他 file:// |
| `allowUniversalAccessFromFileURLs` | file:// 页面可读**任意**本地文件并发网络 |

本页面是 `file://` 加载且注入了 `BubbleNative` 桥 —— 这两条一旦为 true，
页面脚本就能把凭据文件读出来。

**三道拦截**：页面导航（`shouldOverrideUrlLoading`）、子资源
（`shouldInterceptRequest`）、新窗口（`onCreateWindow` 返回 false）。

⚠️ 判据用「是不是白名单目录里的文件」而不是「是不是 file://」——
后者允许加载凭据。且用 `canonicalPath` 防路径穿越。

**修掉一个真实缺陷**：`__pet.pause()` 只暂停 `active`，而页面是 A/B 双缓冲，
`standby` 会一直循环解码 —— 「球隐藏了但还在发热」的来源之一。

**锁屏暂停**：`hide()` 已 release（彻底），但**锁屏时球仍在**（后台悬浮窗
不受锁屏影响），WebView 继续解码。实测场景：开着球锁屏睡觉，早上手机烫且
掉 20% 电。

### G6 第六轮：把空转的钩子接上 ✅

上一轮 `onScreenLocked()` 零调用方。本轮接上，并补上节能暂停。

**注册在服务而不是 Activity**：球在**后台**显示，锁屏恰恰发生在后台；
Activity 可能已被销毁，它的接收器也就没了。前台服务是唯一「锁屏时仍活着」的组件。

**三个 action 都要**：`SCREEN_OFF` 暂停、`SCREEN_ON` 恢复、
`USER_PRESENT` 恢复。⚠️ 第三个容易漏 —— 亮屏后仍可能是锁屏界面，
那时球不可见，真正该恢复的是「已解锁」。

**节能要停三样，不只是视频**：解码、帧动画、**物理循环**。
第三项最容易被漏 —— 球停在那里看起来「没动」，但 `postOnAnimation`
每帧算重力/碰撞，那是持续 CPU 占用。

**用两个信号**：`POWER_SAVE_MODE_CHANGED` + `BATTERY_LOW`。
只监听前者的话「电量 5% 但还没开省电」会继续耗电 —— 而那正是最需要停的时刻。

## 六点十、G7 第一块：设备能力骨架 + 相机 ✅

设计说明 §4.14.1 的四层权限模型（系统授权 / 基座能力 / DSH 审批 / 单次范围）。
本块只做前两层 —— 后两层涉及业务语义（「这次录音能不能上传」），不该在这里定。

**三态而非布尔**：`READY` / `NEED_PERMISSION` / `NO_HARDWARE`。

⚠️ 必须区分「无硬件」与「无权限」—— 用户可操作性完全不同。合并成「不可用」
会让用户白跑设置页，而文档明确要求「硬件无该能力时必须有**真实发现及明确拒绝**」。

**相机用 Camera2 而非 CameraX**：文档要求「最小补丁」。CameraX 约 3 MB 依赖，
我们只需「发现 + 打开验证」—— Camera2 是系统 API，零新增依赖。

**发现阶段不打开相机**：发现就占镜头会让用户看到「相机被占用」通知，
而用户还没做任何操作。

**四类失败明确区分**：`NoHardware` / `NoPermission` / `Busy` / `Failed`。
文档要求「不能用空数据通过」，而 null 无法区分这四种。

**Manifest 权限**：相机/位置/蓝牙（两套按版本）/传感器，全部 `required="false"`
（本应用要能在无相机设备上安装）。`BLUETOOTH_SCAN` 加 `neverForLocation`，
API 31+ 不需要位置权限就能扫蓝牙。

### G7 第二块：音频采集 + 背压 ✅

**刻意「只采集，不外发」**：文档最强调的一条。所以**没有任何网络代码**、
不持有任何上传通道，数据只通过 Sink 回调交给调用方。「要不要发出去」是
调用方的决定且**必须单独授权** —— 本对象不提供任何「顺手发出去」的便利。

**背压必须丢旧保新**：

| 策略 | 后果 |
|---|---|
| 阻塞生产者 | 采集缓冲溢出，音质断续且**延迟累积** |
| **丢最旧的** | 延迟恒定，代价是丢一小段 |
| 中止整个流 | 太激进（偶尔一次消费慢就断流） |

实现：环形缓冲 + 独立消费线程。采集永不阻塞，容量 500ms。

验证 4 场景：正常不丢、**满时丢旧保新（保留第 2 块而非第 1 块）**、
回绕正确、单块超容量不死循环。

**撤权立即停止**：`AudioRecord.read` 撤权时抛 `SecurityException`，
捕获后立即 `release()`，`EndReason` 标为 `PermissionRevoked` ——
不是笼统的「停了」，文档要求「声明终止原因」。

### G7 第三块：位置能力 ✅

文档：「单次定位，用户**显式启动**的持续订阅及停止；定位关闭、超时、
精度/来源说明、版本后台限制；**持续订阅不等于允许后台定位**」。

**最要紧的一条**：用户点「开始持续定位」的含义是「**在我看着的时候**
给我位置」，不是「允许后台一直定位」。两者在 Android 上是不同权限。

本实现**刻意不申请后台定位**（极高敏感度），退后台时**自动暂停**，
回前台恢复。⚠️ 用 `removeUpdates` **真停**而非只忽略回调 ——
后者仍让系统持续定位，耗电且定位图标常亮。

**用 LocationManager 而非 FusedLocation**：后者需 `play-services-location`
（约 1 MB + 依赖 Play 服务），而本项目侧载分发不假设 Play 可用。零依赖。

**三个必须处理的点**：
1. 先查定位服务是否开着（关着时 `requestLocationUpdates` **不抛错也不回调**）
2. 必须有超时（室内可能永不回调，UI 会一直转圈）
3. 拿到结果立刻 `removeUpdates`（否则一直收回调耗电）

**四类结果明确区分**：`NoPermission` / `LocationDisabled` / `Timeout` / `Ok`。
⚠️ 前两者用户可操作性完全不同 —— 一个是给应用权限，一个是打开系统开关。

**权限三级** `FINE` / `COARSE` / `NONE`：只给粗略位置时 GPS 用不了，
只能网络定位，精度差很多，必须说明否则用户以为「定位坏了」。

### G7 第四块：传感器能力 ✅

**三层抽象刻意不混**：类型发现（一次性）/ 原始采样流（50~200Hz）/
语义事件（事件驱动）。混在一起的话，想做算法的插件拿不到原始值，
而只想要「摇了一下」的插件被 200Hz 数据淹没。

**频率用枚举而非裸数字**：`UI`(16Hz) / `GAME`(50Hz) / `FASTEST`(200Hz) ——
让调用方**看到**「我选的是最耗电那档」，传个裸数字 200 不会让人意识到代价。

**⚠️⚠️ 修掉 Android 传感器的经典坑**：`SensorEvent` 对象是**复用**的，
不复制 `event.values` 的话缓冲里存的全是最后一次的值 —— 而代码看起来完全正常。
验证脚本复现了：不复制存 3 条实际全是 `[2,2,2]`，复制后是 `[0,1,2]`。

**背压丢旧保新**：传感器回调在**主线程**上，阻塞回调会 ANR。
环形缓冲 + 独立消费线程（与音频同一套），容量 64 条（50Hz 约 1.3 秒）。

验证：写 6 条到容量 4，丢弃 2，保留 `[2,3,4,5]` ✅

### G7 第五块：蓝牙/BLE ✅

文档：「设备发现、连接生命周期；BLE 服务发现、特征读写和通知订阅；
Android 版本对应授权、关闭/断连、超时、取消、释放；
**不承诺所有经典蓝牙传输和专有设备协议**」。

只做**通用 GATT 操作**，不做经典蓝牙传输协议（SPP/A2DP）与厂商专有协议 ——
后者需要具体设备协议文档，是插件的事。

**API 31 权限分水岭**（最容易写错）：

| API | 扫描权限 | 连接权限 |
|---|---|---|
| ≤ 30 | `BLUETOOTH_ADMIN` + **`ACCESS_FINE_LOCATION`** | `BLUETOOTH` |
| ≥ 31 | `BLUETOOTH_SCAN` | `BLUETOOTH_CONNECT` |

⚠️ 旧版扫描**必须有位置权限**，不给就扫不到任何设备，而错误信息只报
`SecurityException` 或干脆无回调 —— 完全看不出是缺位置权限。

**地址占位符陷阱**：API 31+ 无 CONNECT 权限时 `getAddress()` 返回
`02:00:00:00:00:00`，**看起来像合法地址**。不判会拿它去连接然后莫名失败。

**GATT 必须串行**：Android 不支持并发操作，同时发两个第二个返回 `false`。

**通知订阅必须写 CCCD**：`setCharacteristicNotification(true)` 只是本地开关，
真正让设备发通知的是写 CCCD 描述符。只做前者：本地以为订阅了，设备从不发数据。

**诚实的边界**：读写只报「请求已发出」而非「已完成」—— 真正的结果在
`onCharacteristicRead/Write` 回调里，完整实现需要请求-响应配对。

### G7 第六块：音频播放 ✅

**两侧背压策略刻意相反**（这是重点）：

| 方向 | 策略 | 理由 |
|---|---|---|
| 采集 | **丢旧保新** | 采集不能阻塞；丢一小段延迟不变 |
| 播放 | **阻塞生产者** | 播放丢数据会听到**咔哒声/破音** |

⚠️ 两侧写在不同的类里，不解释清楚的话后来者会以为「应该一致」而改错。

**阻塞写入必须有上限**：`WRITE_BLOCKING` 在蓝牙断开/扬声器被独占/HAL 卡住时
可能永久阻塞。设 2 秒上限，超时丢弃并计数。

**⚠️ 播放器不做文件读取**：文档 §4.13「不允许播放器按任意外部路径读取文件」。
所以只接受**已解码的 PCM 字节**，不接受路径 —— 即使调用方被恶意插件控制，
也只能播它自己解码好的数据。

**`formatForCapture()` 闭环**：采集 16kHz vs 播放默认 44.1kHz，直接回放会
**变速 2.76 倍**，而错误信息不提示。⚠️ `CHANNEL_IN_MONO`(16) 与
`CHANNEL_OUT_MONO`(4) 是不同常量，混用会得到 `getMinBufferSize = -2`。

### G7 第七块：相机真正拍照 ✅

之前 `takePhoto()` 只做「打开相机再关闭」—— 是能力验证，**不产出图片**。
本轮补上完整链路：

```
openCamera → createCaptureSession(ImageReader.surface)
  → TEMPLATE_STILL_CAPTURE → onImageAvailable → JPEG → 落盘
```

**输出在受管目录**（文档 §4.13「不允许播放器按任意外部路径读取文件」）：
落 `filesDir/camera-out/`，**不落 `/sdcard/DCIM`** —— 插件只能通过资源句柄引用。

**文件名用内容哈希**（文档「真实文件内容哈希用于校验和去重，**不用字节数
代替内容指纹**」）：`sha256(bytes)[:32].jpg`，已存在则不重写。
按字节数去重的后果：两张不同的 200KB 照片会被当成同一张。

**旋转用 EXIF 而非转像素**：转像素 = 解码+旋转+重编码 → **二次 JPEG 压缩**
质量下降。用 EXIF 只改元数据。⚠️ 用 `ExifInterface` 不手写解析器
（后者遇厂商私有段会错位）。

**空数据必须拒绝**（文档「不能用空数据通过」）、**10 秒超时**
（`onImageAvailable` 在镜头故障时可能永不回调）。

### G7 第八块：相机录像 ✅

**录像是最容易失控的能力**：拍照是一瞬间，录像会**持续写磁盘**。
不设限的话用户忘了停，一次录满磁盘 —— 而写满磁盘会让**整个 App 失效**
（引擎、日志、会话全都写不了），不只是录像失败。

| 保护 | 值 | 理由 |
|---|---|---|
| 开始前查空间 | ≥ 200 MB | 写满磁盘会让整个 App 失效 |
| 时长上限 | 60 秒（可配） | 到时**自动停止并保存**，不是丢弃 |

**⚠️ 核心坑**：`MediaRecorder.stop()` 在录制 < 1 秒时抛 `RuntimeException`，
而**文件仍然有效**（只是很短）。catch 到异常就删文件的话，用户会
「明明录了却什么都没有」。正确做法是 catch 后**检查文件大小**。

**双保险的时长上限**：`setMaxDuration`（MediaRecorder 自身）+ `postDelayed`
（我们的兜底）—— 只靠前者信息回调在部分机型不可靠，只靠后者
MediaRecorder 内部可能已停止写入。

### G7 第九块：语义事件检测 ✅

文档：「摇动、**姿态**、旋转等**语义事件**」。

**为什么需要语义层**：从原始加速度推出「翻转了」需要低通滤波 → 求重力方向
→ 判断象限变化 → 去抖。每个插件自己写的话阈值不一、大多漏掉去抖、少数用错坐标系。

**三个必须做对的点**：

| 点 | 做法 | 不做的后果 |
|---|---|---|
| 用重力而非原始加速度 | `TYPE_GRAVITY` 或 `GravityFilter` | 「走两步」被识别成「翻转」 |
| **滞回** | 进入 `z<-0.7`、退出 `z>-0.5` | 手抖在阈值附近来回 → 反复触发 |
| 去抖 | 800ms 最小间隔 | 快速翻来翻去连续触发 |

验证：8 帧手抖输入 → 有滞回触发 **1 次**，无滞回触发 **2 次**。

**⚠️ 实现中修掉一个真实缺陷**：`lastFlipAt` 初始值写成 `0L`，导致
**第一帧在 800ms 内被吞掉** —— 表现为「翻转检测完全不工作」。
改为 `Long.MIN_VALUE / 2`。这类缺陷编译和阅读都发现不了，只有跑算法才暴露。

**抬腕的几何判据**：`z > cos(45°)` 且 `y < -0.3`。
⚠️ 只判 z 的话「平放桌面」也会触发 —— 而那不是抬腕。

## 六点十一、G8 第一块：受控修复 ✅

文档：「修复计划**声明范围与不可逆副作用**，批准**绑定目标/参数/环境/epoch/
通道/有效期**，**执行前再核验**」。

**为什么需要「批准绑定」**（最危险的一处）：

```
t=0  AI 生成修复计划，弹窗给用户
t=1  用户去泡咖啡
t=2  期间 AI 又改了计划 / 环境已经变了
t=3  用户回来点「同意」→ 执行的不是他批准的那个
```

6 项绑定各防一类问题，验证 8 个场景全过。

**⚠️ 绑 epoch 的具体时间线**：用户在 A 提交计划（epoch=3）→ 弹窗期间引擎崩溃
自动降级到 R（epoch=4）→ 用户回来点同意。只绑 planId 的话会在 **R 环境**
执行「修 A」的计划。绑了 epoch 就能检测 3→4 不符并拒绝。

**「修复模型不能替代监督器」**：AI 只能 `propose`，批准必须由用户动作
`approve`，执行前由本对象核验 —— 不是 AI 自查。⚠️ 更隐蔽的是**不能以插件
自报 `approved` 通过**：`Approval` 构造函数是 `internal`，外部无法伪造。

**不假报已撤销**：`summary()` 只说「做了什么」「什么没做」，**不承诺「已回滚」**
—— 删除配置无法回滚。

### G8 第二块：诊断 → 修复计划 ✅

把 `DiagnosticBundle`（发现哪里坏了）与 `RepairControl`（受控执行）串起来：

```
DiagnosticBundle → 【映射】 → propose → 用户批准 → run
```

**三条设计纪律**：

**① 没有对应修复时如实说「没有」，不硬凑**

`disk-space`（磁盘不足）与 `heap`（内存不足）**刻意不提供自动修复** ——
删什么？删用户数据？那是不可接受的。硬凑「清理缓存」只会让用户以为修好了，
而实际问题仍在。

`boot-tier`（降级）同理：降级是**结果**不是**原因**，直接重置会让用户
再次陷入同一问题，且丢掉排查线索。

**② 修复动作必须精确到目标**：「重解包引擎」精确到 `engine/`，
「删日志」精确到 `logs/`。含糊的「清理一下」既无法绑定批准也无法核验结果。

**③ 不可逆副作用自动推导**：从 `Kind.reversible` 自动算，不让调用方手写 ——
避免「写漏了某个不可逆动作」，漏写的后果是用户以为可回滚但数据已经没了。

**循环依赖的处理**：刻意不直接引用 `DiagnosticBundle.Check`（`log` 包），
而是定义同构的 `Finding` —— 因为 `log` 包已在依赖 `manage`。

### G8 第三块：修复后核验 + 插件精确映射 ✅

**核验闭环**：没有核验的话流程是「执行 → 返回成功 → 结束」，而
**执行成功不等于问题解决**：

| 场景 | 执行 | 实际 |
|---|---|---|
| 重解包引擎 | 成功 | 资产本身损坏 ⇒ 新解包也坏 |
| 删日志目录 | 成功 | 磁盘满 ⇒ 新日志立刻写失败 |
| 隔离插件 | 成功 | 还有另一个坏插件 ⇒ 仍起不来 |

**四种结论**：`FIXED` / `IMPROVED` / `UNCHANGED` / **`WORSENED`**。
⚠️ 必须有 `WORSENED` —— 修复本身可能出错（重解包时磁盘满 → 解了一半 → 更坏）。

**用集合而非数量**：修复前 1 个问题(a)、后 1 个问题(b)，只看数量是「没变化」，
实际是「修好 a 但弄坏 b」。集合对比能识别 `WORSENED`。

**被拒绝时不核验**：什么都没做时核验必然是「无变化」，报给用户会让他以为
「修了但没用」。返回 `UNKNOWN` 而非 `UNCHANGED`。

**插件精确映射**：原来 `boot-tier` 只说「已隔离 N 个」，现在读
`rescue/state.json` 列出**具体包名**。⚠️ 只列出不自动恢复 ——
恢复坏插件会再次让引擎起不来。

⚠️ **为什么需要句柄而非路径**：若 API 是 `play(path)`，插件可传

同一 UID 下没有强制隔离，文档也承认「不能宣称能隔离恶意插件」。
它是**合作式约束**：让正确用法很容易、错误用法需刻意绕过。

**本轮补第 5 条**：`manage/RepairSnapshot`（448 行）—— 修复前一致快照。

⚠️ **按声明范围快照，不是整个目录**：计划可能只改一个 `package.json`，
快照整个 `$DSH_HOME`（几百 MB）会耗时几十秒，且**快照本身可能让磁盘满** ——
反而制造故障。

四个关键设计：记录「当时不存在」（回滚时删新建的）、**回滚后校验哈希**
（不校验则「恢复了」只是猜）、符号链接记目标不跟随、**快照失败就中止修复**
（没有快照就修是不安全的）。

⚠️ **重要的诚实说明**：本对象不保证「修复一定可撤销」，只保证「快照范围内的
文件内容能恢复」。外部动作与「用户的决定」本身无法撤销 —— 那正是文档要求
「不得报告为已自动撤销」的原因。

**本轮补第 19 条**：`device/CapabilityRequests`（254 行）—— 去重/配额/取消。

⚠️ **实现中修掉一个设计问题**：第一版按能力统一配额（相机=1），验证暴露
「用户先拍后置占满配额，再点拍前置被拒」—— 而换镜头是完全合理的意图。
修正为相机实际配额 `limit+1`，由底层 `openCamera` 报 `ERROR_CAMERA_IN_USE`
（它明确知道「现在真不能开」），而不是我们这层假装知道。

**麦克风不放宽**：第二个会拿到静音数据（系统行为）。

**去重判据含参数且顺序无关**：只按能力去重会让「拍后置」和「拍前置」被当成
同一个请求。⚠️ 去重条件还含「未取消」—— 否则用户取消后重新发起会被挡回
那个已取消的请求。

## 八、最大阻塞：真机验证

**G1 之后几乎每一步都要求真机**：

| 要求 | 为什么本机做不了 |
|---|---|
| 真实文件锁互斥 | 需 Android 的 fcntl 语义 |
| PTY 输入/resize | 需真实终端 |
| 子代理/后台任务 | 需真实进程树 |
| 安装与二进制执行 | 需真机装 APK |
| 权限/审批模式 | 需真实权限系统 |

**这不是「可以绕过」的阻塞** —— 开发指导 §G1「失败处理」明确：
需要禁用锁、假报 full enforcement 时不进入下一阶段。

## 九、下一轮计划

按依赖顺序，**不需要真机**就能做的：

1. **G2 收尾**：无扩展原生恢复入口（原生 Activity，不依赖引擎）
2. **G3 第一块**：诊断副本（复制 profiles 到 cache 再跑 dump-config）
3. 补 G1 闸门二的文案核对收尾

需要真机才能推进的：G1 剩余、G2 的 E 环境验证、G3 之后全部。
