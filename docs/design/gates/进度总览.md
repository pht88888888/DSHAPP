### G2 第四轮补充：E 环境独立依赖树 ✅

新增 `EmergencyEnv`（独立目录 + 版本戳 + 空间检查 + 两段式部署）。

**为什么 E 必须预先解包**（文档 §6.5.4「不能依赖故障发生后才解包」）：

| 场景 | 事后解包会怎样 |
|---|---|
| 磁盘快满 | 解到一半 ENOSPC，半成品比没有更糟 |
| engine.bin 损坏 | 解包失败，E 也起不来 |
| 用户急着救数据 | 要等 15 秒 + 可能失败 |

所以在**正常启动成功后异步部署**（不在启动路径上，否则每次启动多等十几秒）。

**磁盘代价如实标注**：独立依赖树 = 再解包约 120~160 MB。
`shouldDeploy()` 有三条拒绝条件，空间不足（<350MB）时**不部署并如实报状态**，
不硬塞把用户磁盘占满。

**部署顺序的安全性**：`写 staging → 旧 E 改名 .old → staging 改名 E → 删 .old`。
不是「先删再放」——那样断电会两头落空。实测验证：就位失败时旧 E 保住
（stamp 仍是旧值），移开失败时无损。

**启动决策**：`shouldLaunch()` 关键一条是「**一号健康时不切 E**」——
E 是最后一道门，不是更好的选择。切过去会丢用户当前会话与正在跑的任务。

### G2 第五轮补充：完整恢复链 ✅

新增 `RecoveryChain`（A→R→E→原生恢复页）+ `RescueBoot.Tier.EMERGENCY`。

**解决两个核心问题**：

**① 无限重启** —— 现有降级是「失败就往下退一格」，但退到底之后没有出口，
会变成「E 起不来 → 重启 → 还是 E → …」。文档明确禁止。现在能判出 GIVE_UP
并**不启动引擎**，直接进原生恢复页。

**② 不重置 A** —— 文档：「留在 R 诊断 A，不重置 A」。决策器只决定去哪，
不做任何修改。

**关键细节**：

- 一号不可用时**跳过 R 直接进 E**：R 用的还是一号内核代码，一号文件坏了
  R 必然也起不来，硬试只是白等 15 秒
- 用 `emergencyJustTried` 而非 `tier == EMERGENCY` 判无限重启：tier 是持久化的，
  光看它会导致每次启动都 GIVE_UP，用户连手动重试的机会都没有
- R 记录但本次未试 → 再试一次（用户可能刚修好）

**加枚举值后编译器逼着补了 3 处 when 分支**，每处文案都强调性质区别：
救援/安全模式是「同一套内核换配置」，应急模式是「**换了内核**」——
排查方向完全相反。

### G4 核心：加密备份（7 个组件）✅

| 组件 | 职责 | 验证 |
|---|---|---|
| `BackupCrypto` | PBKDF2 + AES-GCM 分段 + HMAC 整包 | **6 场景**：往返/错密码/篡改/截断/重排/头部篡改 |
| `BackupBundle` | 目录↔明文 zip 流、解压炸弹防护 | 编译验证 |
| `BackupManifest` | 清单（加密在包内，不进明文头） | — |
| `BackupRotation` | 三份轮换、失败包不挤占 | **7 场景** |
| `BackupPublisher` | SAF 写入 + 读回验证 | 编译验证 |
| `BackupScheduler` | eventId 去重、防备份风暴 | **6 场景** |
| `BackupOrchestrator` | 串起完整流程 | 编译验证 |

**密码学选型**：复用 JDK 标准实现（文档要求「不自创算法」），无第三方依赖。
PBKDF2 210k 迭代实测 1551 ms；内存恒定（流式）。

**最关键的两个验证**：

1. **加密容器 6 项全过** —— 特别是「段重排」和「截断」，
   这两项是分段 GCM 单独做不到的，靠末尾 HMAC 兜住
2. **防备份风暴** —— 模拟「用户打开 1 次 + 维护续启 5 次」，
   总共只触发 1 次备份（否则会无限循环填满用户磁盘）

### G4 第二轮补充：端到端打通 ✅

| 新增 | 内容 |
|---|---|
| `BackupConfig` | 密码 Keystore 包裹（**不存明文**）、SAF URI、开关 |
| 原生桥 5 方法 | status / setPassword / chooseDir / setAutoEnabled / runNow |
| 设置页「备份与恢复」 | 状态、设密码、选目录、开关、立即备份、5 条说明 |
| 自动备份接入 | 引擎就绪登记 → onUiReady 后延迟 30s 执行 |

**关键设计**：

- Keystore 密钥**不可导出** ⇒ 拿到密文换台设备也解不开。
  备份包本身的加密用**用户密码**，所以重装后输密码仍能解密 ——
  Keystore 丢了只影响「自动备份要不要重新输密码」。这正是文档要的
  「不能用 Android Keystore 代替可跨设备输入的密码」。
- `backupRunNow()` **只代表受理，不代表成功**（成功看 lastSuccessAt）——
  把「已受理」说成「成功」会让用户以为有备份，实际可能失败在加密阶段。
- 自动备份用 `onUiReady` 而非「引擎就绪」：后者只说明服务起来了，
  页面可能还是白的；此时停引擎备份，用户看到「刚打开就卡住」。

### G3 第二轮：事务状态机 + 锁顺序 ✅

**`UpdateTransaction`**（433 行）：五阶段提交，单一可判定提交点。

设计说明要求「**不各写一个互不相关的『当前版本』**」——做法是让激活记录
（`Active`）成为唯一真相源，只有一个字段决定用哪套组合：

```
active == "candidate" ⇒ 新组合；否则旧组合
```

**没有第三种可能**，所以「无法判定」在构造上不可能发生。

两个关键设计：

- **提交点必须一次写入**：`commit()` 同时改 phase 与 active。分两次写的话，
  崩在中间会得到「判定为未提交，但候选已部分接管」的矛盾状态。
- **判定用 active 而非 phase**：phase 可能停在 COMMITTING，而 active 一旦是
  CANDIDATE 就意味着「候选已该接管」。active 是**承诺**，phase 只是**进度**。

验证 7 个崩溃点全部判定正确；提交后与未提交的状态集**无交集**（无歧义）。

**`ManageLockOrder`**（206 行）：监督锁 → 环境锁 → 发布锁固定顺序。

死锁分析：若允许任意顺序，`T1: 拿监督锁等环境锁 / T2: 拿环境锁等监督锁`
立刻死锁。只允许 1→2→3 递增后，循环等待在**构造上**不可能。

第二条规则更隐蔽：「**禁止边持锁等待用户无限输入**」——持锁弹对话框、
用户去吃饭、整个管理面卡住且没有报错。

### G4 第三轮：导入端到端 ✅

新增 `BackupImporter`（三步分离）+ 4 个桥方法 + 设置页导入区。

**三步分离**（安全的关键）：

```
① inspect()  只读：解开头部 + 密码验证 + 出清单   ← 不改任何东西
② stage()    解到私有暂存区并逐文件校验            ← 只写 cache
③ apply()    建恢复点 → 替换 → 失败可回滚          ← 唯一动 A 的一步
```

用户在 ① 之后能看到「这个包是什么、会覆盖什么」再决定。

**实现过程中修掉一个数据丢失级缺陷**：

第一版无条件把全部目录移进恢复点，于是「备份里没有 skills、当前有 skills」时：
skills 被移走 → 因为没源而不复制 → 恢复点被删 → **用户 skills 永久丢失**。
实测验证暴露了它。修复后只移走「备份里确实有」的目录。

### G4 第四轮：profile 恢复 + 依赖一致性 ✅

**问题**：备份纳入了 `profiles/web/{package.json, cordis.patch.yml}`，
但恢复只处理 5 个目录，**不含 profile** —— 「备份了配置但恢复不回来」。

**修法：逐文件恢复，不整体替换目录**。⚠️ 不能整体替换 `profiles/web/`：
那目录里还有 `node_modules`（几百 MB），整体替换会把用户的插件安装状态
换成备份时的（可能已过期），且导入时间从秒级变分钟级。

**依赖一致性校验**：文档要求「不盲目混合两套依赖图」。真实场景是
备份的 `bundles` 清单里有某插件，但包实体没进备份（可从 npm 重装），
恢复后「清单说启用 X 但 X 没装」—— 引擎报错只指向包名，用户不知道
这是「导入了一份来自别的机器的备份」导致的。

⚠️ **只提示不自动修改**：自动摘条目会改变用户的插件配置，必须是显式动作。

验证：正常恢复（配置换成备份版、**node_modules 保住**）、中途失败回滚
（配置恢复成当前版、node_modules 保住）。备份↔恢复**完全对称**。

## 六点八、G5 第一块：LayoutAdapter ✅

设计说明 §4.9 要求「原生窗口处理 + **单一布局适配器** + 局部界面增强」三层结构。

**精确阈值**（文档原文，用整数交叉相乘避免浮点误差）：

| 条件 | 布局 |
|---|---|
| 手动 mobile / official | 锁定 |
| auto 且 r > 4/3 | official |
| auto 且 r < 3/4 | mobile |
| auto 且 **3/4 ≤ r ≤ 4/3** | **保留上次；初次 mobile** |

**为什么必须换掉现有实现**——现有 `client.js` 用 `innerWidth < 1024` +
「非桌面指针」，文档逐条否定了：

| 现有做法 | 文档要求 | 后果 |
|---|---|---|
| 宽度阈值 | **宽高比** | 分屏变窄但仍是宽屏比例，误判 |
| 无滞回 | **3/4~4/3 保留上次** | 阈值附近抖动导致布局横跳 |
| 看指针类型 | **不看鼠标** | 平板接鼠标突然变桌面布局 |

**滞回实测**：窗口从 r=1.343 缩到 1.204，布局一直保持 official 不切换。

**原生侧的关键细节**：高度必须**不含 IME** —— 文档明确「不用键盘缩小后的
visualViewport 误判方向」。用 `WindowMetrics` + `getInsetsIgnoringVisibility`
而不是 visualViewport。

**不重建 Activity**：`configChanges` 已含旋转/分屏，布局变化用
`evaluateJavascript` 推事件而非 `loadUrl`（重载会丢草稿）。

### G5 第二轮：前端接入（判据归一）✅

之前 LayoutAdapter 能算了，但前端还在用旧的 `innerWidth < 1024` + 指针判断 ——
**两个布局执行者**，正是文档禁止的。

`mpIsMobile()` 是唯一入口（40 处调用），只改它的判据来源：

```
① 读 window.__DSH_LAYOUT__（原生算好的）
② 没有 → 退回旧的宽度+指针判据（降级）
```

`data-mobile` 由 `mpSyncMobileAttr()` 统一维护，控制所有 CSS 作用域 ——
改一个函数同时改 CSS 与 JS，不会判据不一致。

**两个关键细节**：

- **初始化必须主动拉一次**：原生可能在页面加载**之前**就推送过布局，
  那次推送发生在还没有监听器时，等于丢了。不主动拉的话首屏会用降级判据
  建出错误界面再被修正，用户看到闪一下。
- **`dsh-layout-changed` 与 `resize` 并存但不是冗余**：后者每次尺寸变化都触发，
  前者只在**实际布局切换**时触发（因为有滞回）。「布局没变但尺寸变了」时
  前者会触发重建（闪烁），后者不会。

验证判据优先级 7/7：原生 mobile + 宽屏 → mobile（原生说了算）；
无标志 + 窄屏 + 有鼠标 → official（桌面缩窗不受影响）。

### G5 第三轮：布局设置 UI ✅

上一轮桥就绪了但用户没地方改，本轮补上设置入口。

⚠️ 文档「**设置所有者与布局执行者分开**」：本节只保存偏好，
实际布局由原生 LayoutAdapter 决定，**从不自己算**。

UI 含：当前设置值 + **实际布局**（两者分开显示，用户能看到「我设的是 auto，
实际用的是手机布局」）、三个模式按钮、自动模式的三条规则、三条注意事项。

**为什么把规则写进 UI**：用户看到「横过来还是手机布局」时最需要知道规则本身。
滞回区间（3/4~4/3 保留上次）如果不解释，用户会以为坏了 —— 而实际是刻意设计。

### G5 第四轮：四类清理 ✅

文档要求「清理**样式、监听、观察器与借用控件**」。

盘点「进入时创建」vs「退出时清理」发现三处真实缺陷：

| 资源 | 问题 | 症状 |
|---|---|---|
| `mpCloseTimer` | 未清理 | 拆解时若还在飞，回调会点官方 toggle —— **退出移动布局后侧栏莫名折叠一次** |
| `mpCenterRaf` | 未清理 | 回调在 `data-mobile` 摘除后继续写 CSS 变量，把居中偏移留在官方布局上 |
| CSS 变量 | 依赖外部调用 | teardown 不自洽；变量会**继承给子元素** |

**刻意不做的两件事**：

- `mpShellBuilt` 不复位 —— 全局监听器只该注册一次，复位会重复注册三个监听器（都泄漏）
- `mpStatusTimer`/`mpTranscriptTimer` 不清 —— 它们是全局的，与移动模式无关

清理覆盖 7/7：观察器、定时器、rAF、自建节点、内联覆盖、CSS 变量、标记位。

## 六点九、G6 第一块：悬浮事件闸门 ✅

设计说明 §4.11：「不采用**无规则的最后写入覆盖**」「切换环境时撤销旧租约…
不得继续显示旧任务正在运行」。验收矩阵第 18 条：「**乱序或过期事件不覆盖当前状态**」。

**要解决的真实问题**：悬浮窗状态由多来源并发更新（页面桥、引擎插件、物理 tick、
状态轮询）。没有序号时会「任务明明结束了，球还在转」——因为迟到的旧事件
在 UI 层覆盖了新状态。

**解法两层**：

- **序号**解决同环境乱序：只接受严格大于当前的
- **租约**解决跨环境迟到：环境 A 的 seq=5 在切到 R（seq 归零）后到达，
  `5 > 0` 本会被接受，但租约不符一律丢弃

**接入点很关键**：在 `applyAppearance()` 拦（唯一配置入口），能把旧事件挡在
**落盘之前** —— 落到磁盘再拦就晚了，下次启动会读到它。

`_seq`/`_lease` 是**可选** JSON 字段，不带时视为「当前租约+下一序号」，
不破坏现有调用方。

验证 5 场景全过，含两个关键：旧状态迟到 → StaleSeq 丢弃；
跨环境迟到 → StaleLease 丢弃。
